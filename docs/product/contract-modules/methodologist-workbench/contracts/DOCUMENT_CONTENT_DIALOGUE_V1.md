# Document content dialogue V1

Accepted for implementation by Root under the current owner's request, 2026-10-15.
Extends, never rewrites, DOCUMENT_DIALOGUE_V1. A content question is not a course
preparation instruction or executable command. Voice and reserve remain unchanged.

## Contract

Reuse the private, immutable-source task and exchange archive of0181. Add POST
`/document-dialogues/{task_id}/content-messages` with the existing request UUID,
expected_revision and instruction contract. Same bounded40 exchanges/100 tasks,
lease, exact replay, ownership/FORCE RLS, revision and failure recovery rules apply.
Content messages do not change draft or plan_id; no automatic generation or write
to lessons, courses or assignments. A linked preview already freezes a specific
revision: start a new task for content questions after preview/submission rather
than silently invalidating or rewriting an execution plan. History remains readable.

Response union adds state `answered`, status `supported|not_found|conflict`, answer
<=8000 characters and <=8 citations. Each citation has a server-assigned number,
document_id/title/version/content_sha256/index_revision, chunk_id (64 lowercase hex
text, as generated by ingestion; not UUID) and exact quote
<=1600 characters. Supported/conflict require citations. Not_found may have no
citations or verified quotes explaining the checked scope or an explicit source
limitation; citations never convert an abstention into a supported positive answer.
The model selects only supplied integer evidence-window handles, never quote text.
The server copies the exact selected window into the public quote and derives all
source identity fields. Server rejects invented/bool/duplicate handles, generated
quote fields and external IDs/URLs. Excerpts are
retrieved only from selected current verified source revisions. Every substantive
answer must be source-grounded; missing information requires explicit abstention,
conflicting material requires explanation without inventing precedence. These are
semantic acceptance gates, not claims that a substring validator proves truth.
Invalid provider output is a generic502 with durable invalid_response and refund,
not request-validation422 containing the internal model answer or source excerpts.

GET `/document-dialogues/{task_id}/sources/{exchange_id}/{number}` returns
`{citation,excerpt}` after owner/current-source reauthorization and exact chunk/hash
validation. GET the same path + `/download` returns the existing authorized original
file; no raw storage/public URLs. A changed/unavailable source blocks opening a
citation, while archived answer/quote remains visible with source-stale warning.
GET/reload never invokes a model. Plain text rendering, no model HTML/link execution.

Bounded retrieval: current question plus up to4 prior content exchanges; <=8 chunks,
<=24000 source characters; existing verified index only, no new embedding call.
Each retained chunk contributes at most3000 characters, partitioned without loss
into at most two1500-character evidence windows. The model may select at most8 of
the at most16 window handles. Citations can be broad windows, not word-level
highlights; two windows from one chunk may both be cited, including conflicting
statements in different halves. Every retained window remains a terminal witness.
Recall is untrusted context, not evidence; only newly retrieved chunks are evidence.
Existing saved model routing/budget admission applies, max2000 output tokens,
30s overall/8s transport deadline, no automatic provider/request retry. No new
resource, provider, plan, paid capacity or reserve activation. The30s bound covers
answer production (index snapshot/retrieval/budget admission/provider/parse), not
the full HTTP journey: durable reservation, terminal SQL locking/persistence and
settlement of an in-flight commit/refund have separate database/transport limits.
An unknown HTTP outcome requires explicit GET recovery; no end-to-end30s SLA.

## Ownership, compatibility and gates

Root owns backend schema/service/routes, source validation, tests, integration and
release. Bounded frontend writer owns DocumentWorkbench.tsx, documentDialogue.ts
and focused UI tests only. Independent reviewer is not a writer. No DB migration:
0181 deliberately stores typed exchange objects in JSONB. Old tasks remain fully
compatible. Application rollback55 cannot display new `answered` exchanges; these
new mixed-history tasks must be retained (never deleted/downgraded). Roll forward
is the recovery for new Q&A history; all pre56 preparation tasks remain readable.

Test strict model parser, known quotes/foreign handles, no-answer/conflict, injection,
source race/reload/replay/failure/revision/tenant/actor/role negatives; verify RLS
using the canonical isolated DEV gate. Then actual DEV and production synthetic QA
questions, contextual follow-up, refusal, conflict, citation open and original file,
full reload/reopen, unchanged draft/plan/job counts/routing/reserve/old learning.
CI, protected release and exact runtime identities remain mandatory. Document
observed response quality/timing honestly; substring validation is not an entailment
oracle, small QA samples are not SLA or human-efficiency benchmarks.
