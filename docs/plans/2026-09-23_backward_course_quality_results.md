# Результат первой обратной проверки генерации

Дата: 2026-09-23. Контур: отдельный локальный worktree, только синтетические данные. В DEV, production и tenant DB записей не было. Это первая итерация гипотезы, не заявление о качестве 9/10.

## База и независимые ожидания

Золотые факты и запрещённые утверждения записаны вручную в `apps/api/tests/fixtures/course_generation_backward/corpus.json` до оценки выхода. Четыре случая:

| Источник | Ожидание | Проверка |
|---|---|---|
| Одно правило отмены заявки | Одна тема, не более одного урока и одного самостоятельного проверяемого решения | Карта фактов; локальный полный урок + вопрос через DeepSeek |
| Два раздела регламента приёмки | Оба условия и порядок сохранены, не более двух уроков | Настоящий текстовый PDF -> штатный локальный fallback-конвертер -> `DocumentChunker` -> карта источника -> план |
| Excel «Коллекции» + «Номенклатура» | Коллекции — первичны, артикула — справочные; не более двух уроков | Настоящий XLSX -> штатный `openpyxl` converter -> `DocumentChunker` -> карта источника -> план |
| Неопределённый срок `? рабочих дней` | Не придумывать число; проверять только известное условие комплектности | Карта фактов, план, ось вопроса |

Для PDF проверен локальный fallback `pypdf`, **не** удалённый Docling. Для Excel использован тот же `DocumentConverter`/`openpyxl`, что выбирает приложение для XLSX. Загрузка файла через HTTP, tenant-хранилище, embedding, публикация и браузерный UX в этой фазе не проверялись.

## Проверяемый результат

До изменений короткое правило давало **0 уроков**, потому что единственная секция с заголовком, совпавшим с названием документа, ошибочно получала роль `supporting`. Малый Excel давал **4 урока**: лист номенклатуры ошибочно был учебной темой. После двух узких изменений: соответственно **1 урок**, а Excel **2 урока** с номенклатурой в `supporting`. Двухсекционный регламент даёт **2 урока**; неопределённый источник — **1 урок** без выдуманного срока. Новая база включает настоящие локальные XLSX/PDF-конверсии и проверку исходно привязанных осей вопроса во всех четырёх случаях. Соседние регрессии вместе с новой базой: **201 passed**; проектный Python quality baseline прошёл (`ruff=1056`, `mypy=2227`), `git diff --check` чистый.

Детерминированный черновик не создаёт вопросы для этих четырёх документов — вопросы создаёт отдельный семантический этап. Поэтому один только зелёный тест плана **не доказывает** готовый тест курса.

## Ограниченный живой образец

Первая санкция владельца разрешала максимум 8 генеративных вызовов существующего DeepSeek-аккаунта, максимум $2 дополнительного расхода. В первой фазе сделано ровно **8 вызовов**; продолжение началось только после отдельного указания владельца с общим лимитом $2. Модель `deepseek-flash` (официально DeepSeek-V4.1-Flash), только синтетическое правило; embeddings намеренно выключены для изоляции этапа. Пробный лимит ответа 1800 токенов дал неполный JSON на review и 0 принятых вопросов; при 8192 токенах, как в рабочем клиенте, четыре вызова дали:

- один урок «Отмена заявки до передачи товара», сохранивший исходное условие;
- один ситуационный вопрос о действии сотрудника и один однозначный ключ;
- review/constraint audit принял вопрос после удаления одного дистрактора; курс помечен `publishable=true`;
- три ответа относятся к ситуации, но один неверный вариант вводит отсутствующую в исходнике «службу доставки». Как вариант ошибочного поведения он не становится правилом курса, однако для оценки 9/10 этого одного образца недостаточно.

Начальный диагностический вызов остановился на ошибке адаптера после одного платного ответа; последующие запуски использовали 3 и 4 вызова. Консервативная верхняя оценка затрат по числу запросов и [официальным пиковым тарифам DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/) — **менее $0.07**, фактическое списание отдельно не сверялось в биллинге. Финальный живой прогон длился около 50 секунд; точные метрики каждого этапа не снимались. Проверка против нескольких моделей, длинного документа и повторяемости пока не выполнена.

## Вторая итерация: тот же путь, что у рабочего конвертера

После отдельного разрешения владелец установил для всего эксперимента потолок $2. Скрипт резервирует до запроса максимум по пиковому тарифу DeepSeek и максимальному ответу; журнал переживает перезапуск, конфликт параллельного доступа закрывается отказом. Начальный резерв $0.07 покрывает оценку первых восьми вызовов. В конце зарезервировано **$1.349272 из $2**, то есть предел не достигнут. Это **не** фактический биллинг провайдера: по ответам модели пик-тарифная оценка ниже, но аккаунт DeepSeek здесь не сверялся. После завершения платный запуск стенда закрыт в коде до нового разрешения.

На синтетическом PDF использован штатный закрытый туннель к VM126 и рабочий `DocumentConverter`: сервер вернул `engine=markitdown`, не локальный `pypdf`. На XLSX сработал тот же штатный `openpyxl`, что в приложении. Сохранённые результаты и учёт вызовов — JSON рядом с этим отчётом; содержат только синтетические сведения, без ключа.

Первый рабочий PDF-прогон обнаружил критическое расхождение: оба раздела были в тексте конвертера, но курс включил только второй и всё же получил `publishable=true`. Оказалось, что конвертер выдавал заголовки `1. ...` без `#` и вставлял пустые строки внутри фраз. Исправлены нарезка, паспорт секций и осторожное склеивание продолжений. Зафиксирован точный синтетический вывод конвертера; проверены также вложенные заголовки `1.1 ...` и два коротких раздела по одному правилу. Нумерованные действия не превращаются в заголовки, факты соседних разделов не перекрываются.

Отдельно выяснилось, что первая версия испытательного DeepSeek-адаптера не повторяла одноразовое исправление синтаксиса JSON, предусмотренное рабочим LLM-клиентом. Стенд приведён к тому же контракту и проверен на искусственном неверном JSON без сети. Это исправление тестового стенда, а не продуктового генератора. Предыдущие отрицательные пробы сохранены как диагностическое evidence.

В финальном PDF сохранены три самостоятельных проверяемых действия: остановить разгрузку и сообщить руководителю при несовпадении номеров; осмотреть упаковку после сверки; зафиксировать повреждение в акте до подписания. Неверные варианты теперь отвечают на тот же вопрос и меняют порядок либо обязательное действие. В Excel темы — две коллекции, не номенклатура; пять принятых вопросов в последней пробе относятся к назначению, материалу или отличительной особенности, а не к случайным артикулам. Ручной просмотр не выявил выдуманных правильных ключей или вопросов «о чём этот урок».

Исходный независимый ориентир `distinct_assessable_decisions=4` для Excel **не выполнен**: живые пробы дали 5–6 вопросов. Мы не переписали эталон задним числом. При чтении таблицы видно шесть отдельных утверждений (две коллекции × три атрибута); пять принятых вопросов не дублируют друг друга. Это повод пересмотреть сам критерий плотности в следующем заранее зафиксированном наборе, а не натягивать продукт на произвольную цифру. Даже после улучшения вопросы этого крошечного источника в основном проверяют узнавание свойств, не сложное применение; оценку 9/10 по ним заявлять нельзя.

## Вердикт и границы

**GO для локального кандидата четырёх интерфейсов; NO-GO для самостоятельного production-релиза по этому evidence.** Критерии локальной приёмки: факты и смысловые границы не теряются при конвертации; уроки не раздуваются вспомогательной таблицей; у простого регламента при двух независимых повторах есть по меньшей мере один принятый вопрос на каждую явно проверяемую тему; правильные ответы привязаны к точным исходным фразам; слабые вопросы удаляются без добора квоты. Последние две PDF-пробы и три Excel-пробы этому содержательно соответствуют, кроме оговорённого старого числового ориентира Excel.

Это не полный путь методиста: embeddings намеренно отключены, tenant API/БД/очередь, клиентские крупные PDF/XLSX, браузер и публикация не проверялись. Дополнительно нужен DEV application gate на синтетическом документе, затем релизный exact-SHA процесс и production readback с отдельной санкцией. Нельзя переносить локальный результат на все объёмные документы или обещать качество 9/10.

## Дополнительная проверка на локальном GLM-5.3-Flash-EXL3

После запроса владельца модель `GLM-5.3-Flash-EXL3` подтверждена через
`http://10.66.66.28:8888/v1/models`; короткий JSON-ответ с
`response_format=json_object` прошёл. Удалённый PDF-конвертер — тот же рабочий
VM126/MarkItDown, XLSX — штатный `openpyxl`. DeepSeek в этой серии больше не
вызывался, лимит платного эксперимента не менялся. Контур остаётся локальным:
только синтетические файлы, без DEV/production записей и без embeddings.

Первый полный запрос к GLM без явного режима рассуждения не дал результата за
15 минут; остановлен только наш тестовый процесс. В документации данной EXL3
сборки подтверждено включённое по умолчанию длительное рассуждение и клиентский
параметр `chat_template_kwargs.enable_thinking=false`. После его применения
короткий ответ пришёл за 3.03 с, а полные этапы стали измеримыми. Тестовый
адаптер теперь проверяет HTTP-статус, имеет 600-секундный предел на вызов,
общий предел на прогон, максимум вызовов и пометку времени каждого ответа.
Это настройка стенда, **не** изменение production-маршрутизации моделей.

| Синтетический источник / режим | Вызовы | Уроки | Принятые вопросы | Время реализации / вопросов | Итог |
|---|---:|---:|---:|---:|---|

| XLSX, после обоих исправлений, без рассуждения | 10 | 2 | 6, по 3 на урок | 36.8 / 87.9 с | publishable, без набора голых значений в одном абзаце |
| PDF, после исправления фильтра | 8 | 2 | 3, оба урока | 38.8 / 63.2 с | publishable, правила и порядок не потеряны |

Исходный JSON-ответ GLM в диагностическом прогоне Excel был связным, но
содержал не подтверждённые таблицей советы продавцу. Их удаление правильно.
Ошибка была в том, что постобработка после удаления склеивала `МДФ Для
прихожей Зеркало...` вместо удаления уже дублирующего блока или раздельного
вывода ещё не покрытых фактов. Это исправлено с регрессионными тестами.
Второй дефект: когда проверка удалила все три вопроса по «Берегу», общая
проверка темы не требовала ревью. Теперь блок, у которого были проверяемые
кандидаты, но не осталось ни одного принятого вопроса, делает курс
`review-required`; новых вопросов до квоты не выдумываем. Тесты отделяют эту
ситуацию от действительно непроверяемого источника без кандидатов.

Ручной просмотр последнего PDF: верно сохранены три действия; варианты ошибок
относятся к тому же процессу. Последний XLSX: оба предмета представлены,
вопросы проверяют материал, назначение и особенность, а не вспомогательные
артикулы. Уроки XLSX всё ещё короткие и табличные, это **не** уровень 9/10.
Из последнего PDF устранён технический заголовок «положение» детерминированным
заголовком из начала исходного правила; последняя корректировка длины такого
заголовка проверена юнит-тестом, но после неё полный GLM-прогон **не** повторялся.
Ранее установленный независимый числовой ориентир Excel «4 решения» не
переименован задним числом: отдельные 6 атрибутов дают 6 проверяемых фактов,
но решение об изменении критерия требует новой заранее зафиксированной базы.

Проверка: 221 выбранный локальный тест без БД, проектный Python quality
baseline `ruff=1056, mypy=2227`, `git diff --check`. Ни один тест не доказывает
работу tenant API, embeddings, фоновой очереди и клиентских больших документов.
Вердикт остаётся **GO для локального кандидата, NO-GO для самостоятельного
production-релиза**. Следующий отдельный gate — DEV application flow на
синтетических файлах, затем один живой путь методиста перед релизом.
