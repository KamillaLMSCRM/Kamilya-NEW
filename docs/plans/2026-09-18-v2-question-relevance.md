# V2: уместность ответов и честный результат генерации

## Граница

Исправление активного `evidence_v2`, без изменения источников клиента, схемы БД,
провайдеров и биллинга. Минимальная правка фронтенда: открыть сохранённый
черновик, если проверка не оставила вопросов, вместо бессмысленного продолжения.
TypeSafe — только независимая DEV-оценка
синтетических примеров, не часть клиентского запроса.

## Приёмка

1. Воспроизвести: вопрос о персональных данных с ответами про первый ответ и
   эскалацию не проходит. Соседние правдивые факты не являются дистракторами.
2. Все варианты отвечают на один вопрос, проверяют тот же навык/атрибут;
   неверные варианты — правдоподобные ошибки. Только один верный вариант,
   подтверждённый материалом своего урока. Неполный/ошибочный ответ проверки
   не считается успехом.
3. Одна ограниченная попытка исправить только отбракованные варианты;
   повторная проверка обязательна. Принятые вопросы неизменны. Без увеличения
   числа уроков/вопросов ради квоты. Неисправимые вопросы исключаются.
4. При нуле принятых вопросов уроки сохраняются черновиком, но задача не
   сообщает об успешном создании полного курса с тестами. Доступен course_id,
   понятная причина и реальные счётчики; повтор не создаёт дубликат.
5. DB-free регрессии, тесты активного application seam, реальная ограниченная
   проверка моделью на синтетических примерах, TypeSafe DEV, независимое ревью.
6. После успешной приёмки: exact-SHA API/worker + frontend release без миграций,
   штатные CI/DEV/release gates, readback API и трёх workers, синтетический
   smoke и доказанное удаление временных данных.

## Разделение

- Root: контекстная проверка/ограниченный ремонт, active V2 seam, локальная
  проверка, интеграция и решение о релизе.
- Mill (bounded writer): исход задачи без вопросов, счётчики, регрессии
  сохранения; только pipeline и собственный unit-test.
- Kant (bounded writer): цельные абзацы, условия/исключения, границы разделов;
  затем read-only ревью чужого assessment-кода.
- Mill: также узкая UI-ветка открытия сохранённого черновика с тестами.
- Dalton: достоверность DEV-сценария таблицы и сохранение метаданных колонок.
- Dewey: DEV-адаптер TypeSafe учитывает все цитируемые факты вопроса.
- Root: независимая проверка изменений агентов, результаты реальных вызовов.

## Реализованный порядок

Исходный абзац сохраняется вместе с условиями, исключениями и продолжением
списка. Самостоятельные разделы не склеиваются только из-за малого объёма.
Вопросы создаются заново из блока своего урока, а не из соседних правдивых
предложений. Отдельный вызов модели проверяет каждый вариант: уместность,
истинность, неоднозначность и учебную ценность. Исправление ограничено одной
попыткой и исходной проверяемой темой. Удалённые вопросы не заменяются квотой.

Ноль вопросов — сохранённый черновик с `assessment_no_valid_questions`, а не
успешный курс с тестами. В этом изменении нет автоматического исправления уже
созданных клиентских курсов. Протокол текущей локальной проверки — в
`docs/testing/TEST_RUN_LEDGER.md`; зелёный unit-набор не равен приёмке production.

## Исходное доказательство

Локальный `filter_acceptable_questions` сохраняет точный плохой пример со
скриншота (1 вместо 0). Исходники подтверждают: варианты определяет сервер,
а writer только переформулирует seed. Поэтому одной правки writer prompt мало.
Ранее TypeSafe дал вопросу REVIEW (plausibility 0.54), а не самостоятельный
REJECT; нельзя выдавать отказ всего комбинированного артефакта за оценку вопроса.

## Новый локальный эксперимент: objective alignment, 18 сентября

Разрешён только DEV-эксперимент, без изменения runtime-генератора, БД, tenant,
маршрутизации, frontend, push или production. Источником baseline является
текущий локальный candidate, а не утверждение о текущем production SHA.

1. Root фиксирует SHA256 runtime-дерева и новых prompts до раскрытия holdout.
2. Два знакомых synthetic DEV-источника и два новых holdout, подготовленных
   Luna/medium в отдельном файле. Expected objectives не передаются генератору.
3. По два повтора A/B. A — штатный application seam. B — те же исходные факты
   и source-plan packs, затем цель → teaching block → проверяемое решение.
   Outline/parser/embeddings не являются экспериментальной переменной. Это
   короткий pedagogical-seam pilot, НЕ полная замена движка.
4. Оба плеча используют тот же env-only DeepSeek configuration, temperature=0.2,
   max_tokens=8192, без DB/settings writes. Один transport attempt, не более
   одной syntax correction на вызов; общий предел 30 model calls/arm/case и
   180 секунд. Сохраняются и ошибки, и незавершённые результаты; нет скрытого
   перезапуска неудачных случаев. Порядок A/B меняется во втором повторе.
5. Перед holdout допустим только ремонт harness/нарушения контракта, не tuning
   по holdout. На синтетике TypeSafe report-only и независимое чтение всех
   вопросов и уроков относительно исходника. Runtime self-review не равен QA.
6. Заранее зафиксированные gates для каждого повтора: 0 неподтверждённых
   правильных ответов/опасных добавок; 0 неуместных/дублирующих неверных действий;
   все ответы объяснимы из урока; покрыты >=80% заранее названных meaningful
   целей (округление вверх); нет вопросов про названия разделов/очевидную
   идентификацию. Ноль вопросов, provider failure и недостающее покрытие не PASS.
7. B допускается к двум полным реальным документам только если оба holdout
   повтора проходят gates и количество подтверждённых дефектов меньше A, без
   ухудшения покрытия. Малый pilot не доказывает универсальное качество.
8. Root — engine, runner, acceptance/docs; Luna — только holdout; второй worker
   — независимые contract tests/review. Все результаты в существующем testing
   report/ledger. На неуспехе остановка и итоговое решение, без нового релиза.

Статус: bounded pilot завершён, **NO_GO**. Все16попыток сохранены;19focused
tests PASS. Два ложных validator-отказа исправлены после freeze и проверены
на сохранённых ответах безAPI; не объявлены новой генерацией. Семантические
ошибки и недостаточное покрытие остаются открыты. Большие реальные документы
не запущены, production не изменён. Полный разбор и времена каждого плеча:
`docs/testing/2026-09-18-semantic-block-assessment.md`, раздел
«Локальный A/B после разбора scorm_agents». Автоматическое продолжение остановлено.

## Продолжение по запросу владельца: исследование и локальная приёмка

Владелец попросил продолжать до приемлемого результата и поискать примеры в
интернете. Это возобновляет DEV-работу, но не разрешает изменять runtime или
выпускать эксперимент. Предыдущие отрицательные результаты сохраняются.

Практические основания нового шага:

- [NBME Item Writing Guide](https://www.nbme.org/sites/default/files/2021-02/NBME_Item%20Writing%20Guide_R_6.pdf):
  один сфокусированный вопрос, однородные варианты; проверка ответа до просмотра
  вариантов. Применяются общие принципы, не клиническая валидность этой методики.
- [Carnegie Mellon: alignment](https://www.cmu.edu/teaching/assessment/basics/alignment.html):
  проверяемая цель должна соответствовать объяснению и заданию; наличие вопроса
  на тему само по себе не доказывает проверку нужного действия.
- [Bitew et al., Distractor generation](https://arxiv.org/abs/2307.16338) и
  [авторская реализация](https://github.com/semerekiros/distractGPT/blob/main/fewshot_chatGPT.py):
  примеры хороших вопросов/ошибок как контекст построения альтернатив. Их код не
  установлен и не перенесён в runtime; добавлены собственные учебные примеры.
- [Rodriguez, 2005](https://onlinelibrary.wiley.com/doi/abs/10.1111/j.1745-3992.2005.00006.x):
  не требуется насильно создавать 4–5 вариантов. Исследование трёх вариантов не
  является доказательством равной полезности любого бинарного вопроса.

Порядок реализации и приёмки:

1. Явно хранить нормативную силу цели: обязательно / запрещено / можно /
   не требуется / описание / смешанное. Условия и исключения относятся к той
   же цели, а не к квоте отдельных вопросов. В урок не выводить служебные поля.
2. Слепая проверка получает исходник, цели, готовое объяснение и вопросы без
   ключа/авторских оправданий. Проверяет также искажения в самих целях.
3. Удалять отдельно неуместный/дублирующий неверный вариант. Сохранить хороший
   вопрос с осмысленным контрастом; не добавлять альтернативы ради количества.
   Неприемлемая неоднозначность ключа остаётся отказом, а не произвольной заменой.
4. Одна ограниченная содержательная коррекция, отдельная ограниченная коррекция
   нарушения JSON-контракта; промежуточные результаты и отказы сохраняются.
5. Сравнить фактическое поведение существующего DeepSeek с выключенным и
   включённым рассуждением. Настройка делается только в экземпляре DEV-клиента;
   production env не меняется. Затем проверить выбор режима по этапам.
6. Контрактные positive/negative tests и повторная проверка сохранённых плохих
   ответов без генерации всего курса. Зелёный mock-тест не является semantic GO.
7. После фиксации кода — четыре новых закрытых синтетических случая, два повтора.
   Holdout создан Luna, не передаёт expected_objectives генератору и не служит
   материалом для подбора промптов. Критерии качества прежние, 80% важных целей,
   ноль неверных ключей/искажений правила/неуместных вариантов.
8. При успехе — полные Plus XLSX и Lombard PDF локально с checkpoint на урок,
   временем и расходом каждого этапа. PDF — сохранённый результат штатного
   production Docling с проверкой SHA источника, не альтернативный OCR.
   Никаких записей в БД и клиентских курсов; TypeSafe только синтетика/report-only.
9. Root читает результаты и отвечает за итог; Luna пишет тесты и делает отдельное
   ревью. GO локальному подходу и GO production — разные решения.

Проверено по [документации DeepSeek](https://api-docs.deepseek.com/guides/thinking_mode/):
thinking задаётся на запрос, отдельные ключи для ролей не нужны; temperature
в thinking-режиме не действует. [Лимит параллельности](https://api-docs.deepseek.com/quick_start/rate_limit/)
общий для аккаунта независимо от ключа. Несколько ключей — разделение доступа,
а не увеличение лимита. По странице провайдера старое имя deepseek-v4-flash
является алиасом; в новых измерениях отдельно сохраняется model из ответа API.
