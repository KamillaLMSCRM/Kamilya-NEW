# AI-помощник методолога: рекомендации аудитории курса

**Статус:** реализовано в `master`; production rollout и smoke не выполнялись
**Приоритет:** P1
**Владелец:** роль `methodologist`
**Канонический экран:** редактор курса `/courses/{course_id}/edit`

## Реализация на 2026-07-28

Готово:

- явное намерение `audience_recommendation` и распознавание свободного вопроса;
- tenant-safe read-only снимок курса, структуры, групп, правил, компетенций и
  агрегатов назначений;
- детерминированные приоритеты и ограниченный LLM-контекст без персональных
  данных;
- fallback по явным связям при недоступном LLM;
- структурированная локализованная карточка рекомендации в AI-панели;
- ссылка на канонический экран назначения только для опубликованного курса;
- запрет write-действий и проверки RBAC/cross-tenant поведения;
- unit, integration и frontend-тесты.

Осталось:

- controlled rollout на тестовом tenant;
- read-only production smoke по разделу 9;
- проверка фактической задержки и качества рекомендаций на реальной тестовой
  оргструктуре.

## 1. Продуктовая цель

Помощник должен отвечать на вопросы вида:

- «Кому назначить этот курс?»
- «Каким отделам он подходит?»
- «Есть ли в структуре должности, для которых этот курс обязателен?»
- «Кто уже проходит похожее обучение?»

Ответ строится на содержании текущего курса и фактической структуре текущего
tenant. Помощник объясняет рекомендацию, но не создаёт назначения и не меняет
правила обучения.

Целевой процесс:

`курс → анализ содержания → анализ структуры → рекомендация аудитории → переход на обычный экран назначения → ручное решение методолога`

## 2. Неподвижная граница полномочий

Контур рекомендаций является строго read-only.

Помощник не должен:

- создавать, изменять или отменять `Enrollment`;
- создавать или изменять правила организации, отдела, должности или компетенции;
- менять состав групп сотрудников;
- публиковать курс;
- рассылать приглашения;
- автоматически открывать доступ обучающимся;
- вызывать write-endpoints после подтверждения в чате.

Допустимое действие в ответе — ссылка **«Перейти к назначению»**, которая
открывает стандартный экран `/assignments` с предварительно заполненным
`course_id` и, если возможно, фильтром аудитории. Итоговый список проверяет
методолог, а кнопку **«Назначить»** нажимает только он на каноническом экране.

Существующая возможность применить предложенную AI правку к тексту урока
остаётся отдельной функцией редактора контента. Она не расширяет полномочия
помощника в отношении сотрудников и назначений.

## 3. Исходное состояние до реализации

Сейчас `POST /v1/ai/chat` получает:

- курс;
- структуру модулей и уроков;
- содержимое выбранного модуля или урока;
- вопрос методолога.

Он не получает:

- отделы и должности tenant;
- группы сотрудников;
- компетенции;
- количество подходящих сотрудников;
- действующие правила обучения;
- существующие назначения курса.

Поэтому текущий ответ «в материалах курса нет информации» технически
соответствует переданному контексту, но не решает задачу методолога. В ответ
также попадают внутренние значения `draft` и `review_status`, которые не должны
показываться пользователю.

## 4. Целевой пользовательский ответ

Ответ должен состоять из структурированных блоков:

1. **Рекомендация** — кому подходит курс.
2. **Почему** — темы курса и признаки структуры, на которых основан вывод.
3. **Охват** — число подходящих сотрудников без персональных данных.
4. **Уже назначено** — агрегированное состояние текущих назначений.
5. **Ограничения данных** — чего не хватает для уверенной рекомендации.
6. **Следующий шаг** — переход на экран назначения без изменения данных.

Пример:

> Курс рекомендуется всем сотрудникам, а в первую очередь — IT, кадровой
> службе, финансам, руководителям и должностям с доступом к клиентским данным.
> В текущей структуре этим условиям соответствуют 18 сотрудников в 5
> должностях. Рекомендация основана на уроках о классификации данных, паролях,
> MFA и действиях при инцидентах. Курс пока является черновиком: аудиторию
> можно проверить сейчас, а назначить курс — после публикации.

Кнопки:

- **Посмотреть подходящие группы**;
- **Перейти к назначению** — доступна только для опубликованного курса;
- **Что повлияло на рекомендацию**.

## 5. Архитектура

### 5.1. Не передавать произвольные SQL-инструменты модели

LLM не должна самостоятельно строить запросы к БД или выбирать endpoints.
Backend формирует ограниченный tenant-safe снимок и передаёт модели только
разрешённые поля.

### 5.2. Новый read-only сервис

Создать `AudienceRecommendationService`, который:

1. проверяет принадлежность курса текущему tenant;
2. извлекает учебные темы и цели из названия, описания, модулей, уроков и
   связанных компетенций;
3. получает структуру `department → position → employee_count`;
4. получает группы сотрудников и их размеры;
5. получает существующие правила курса;
6. агрегирует текущие назначения курса;
7. возвращает нормализованный снимок без email, телефона, Telegram ID и других
   персональных полей.

Повторно использовать существующие модели и запросы структуры, но не вызывать
HTTP endpoints из backend-кода. Общую read-only выборку вынести из router в
service/repository, чтобы UI структуры и AI использовали один источник данных.

### 5.3. Определение намерения

`POST /v1/ai/chat` должен различать минимум три намерения:

- `course_review`;
- `content_revision`;
- `audience_recommendation`.

Для надёжности добавить явное действие в UI **«Кому подходит курс?»**. Оно
отправляет `intent: audience_recommendation`; свободный текст может проходить
через ограниченный классификатор. При низкой уверенности помощник задаёт
уточняющий вопрос, а не загружает расширенный контекст автоматически.

### 5.4. Контракт API

Расширить запрос обратно совместимым полем:

```json
{
  "course_id": "uuid",
  "context": "course",
  "target_id": null,
  "message": "Кому назначить курс?",
  "intent": "audience_recommendation"
}
```

Расширить ответ структурированным необязательным объектом:

```json
{
  "reply": "Краткий вывод",
  "audience_recommendation": {
    "course_status": "draft",
    "recommended_scopes": [
      {
        "type": "position",
        "id": "uuid",
        "name": "Специалист по кадрам",
        "employee_count": 3,
        "priority": "primary",
        "confidence": "high",
        "reasons": ["Работа с персональными данными"]
      }
    ],
    "matched_employee_count": 18,
    "already_enrolled_count": 2,
    "data_warnings": [],
    "assignment_url": null
  }
}
```

`assignment_url` возвращается только для опубликованного курса. Это URL, а не
команда на создание назначения.

### 5.5. Логика рекомендаций

Результат должен быть воспроизводимым и объяснимым:

1. Backend формирует кандидатов: вся организация, отделы, должности и cohorts.
2. Детерминированные связи имеют наивысший вес:
   - существующее правило курса;
   - связь курса с компетенцией;
   - связь курса с должностью или отделом;
   - совпадение с утверждённой должностной инструкцией.
3. Семантическое соответствие названий и описаний используется только как
   рекомендация, а не как обязательное правило.
4. LLM формулирует объяснение на основе подготовленных кандидатов и evidence,
   но не придумывает новые отделы, должности или численность.
5. Если надёжных данных нет, ответ сообщает об этом и предлагает настроить
   компетенции или правила обучения.

Приоритеты:

- `primary` — есть явная связь или сильное соответствие обязанностям;
- `secondary` — курс полезен, но обязательность не подтверждена;
- `organization` — содержание является общеорганизационным;
- `insufficient_data` — рекомендация требует решения методолога.

## 6. Privacy, RBAC и tenant isolation

- Endpoint доступен только активной роли `methodologist`.
- Каждый запрос содержит фильтр `tenant_id` на уровне repository.
- Чужие идентификаторы курса, отдела, должности или cohort возвращают `404`.
- В LLM-контекст по умолчанию передаются только названия организационных
  единиц и агрегированные количества.
- ФИО и контакты сотрудников не передаются модели.
- В логах не сохраняется полный снимок структуры или текст с персональными
  данными.
- В API ответа отсутствуют любые write-токены, команды и скрытые операции.

## 7. UX/UI

### 7.1. Быстрые вопросы

В пустом состоянии панели показать:

- «Кому подходит этот курс?»
- «Что стоит проверить перед публикацией?»
- «Какие темы раскрыты недостаточно?»

### 7.2. Карточка рекомендации

Не выводить длинный неструктурированный текст. Использовать компактную карточку:

- статус курса человеческим языком;
- приоритетная аудитория;
- дополнительная аудитория;
- количество сотрудников;
- основания рекомендации;
- предупреждения о качестве данных;
- ссылка на назначения.

Не показывать `draft`, `review_status`, UUID и имена полей БД.

### 7.3. Состояния

- **Черновик:** рекомендации доступны, назначение недоступно; подсказка
  «Опубликуйте курс, чтобы перейти к назначению».
- **На проверке:** рекомендации доступны; показать текущий этап выпуска.
- **Опубликован:** доступна ссылка на `/assignments?course_id=...`.
- **Нет структуры:** объяснить, какие данные нужно заполнить.
- **Нет подходящих групп:** не подменять отсутствие данных общими советами.
- **AI недоступен:** показать детерминированные связи из БД, если они есть.

## 8. Этапы реализации

### Этап A. Контракты и защита границ

- добавить тип намерения и структурированный response;
- добавить тест, запрещающий появление assignment mutations в AI-router;
- убрать внутренние статусы из пользовательского prompt;
- добавить локализованные названия статусов;
- зафиксировать RBAC и tenant isolation.

### Этап B. Read-only контекст tenant

- вынести повторно используемую выборку структуры;
- реализовать `AudienceRecommendationService`;
- добавить правила, cohorts, компетенции и агрегаты назначений;
- ограничить объём данных и исключить PII;
- добавить fallback без LLM на явных связях.

### Этап C. Grounded-рекомендация

- реализовать детерминированное ранжирование кандидатов;
- передавать LLM только кандидатов и evidence;
- валидировать structured output;
- отбрасывать несуществующие ID и названия;
- добавлять предупреждение при низкой уверенности.

### Этап D. Интерфейс

- добавить быстрый вопрос;
- отрисовать карточку рекомендации;
- добавить раскрываемые основания;
- добавить безопасный переход на канонический экран назначения;
- проверить desktop, 768 px и 390 px.

### Этап E. Production rollout

- включить через feature flag для одного тестового tenant;
- проверить токены, latency и fallback;
- провести read-only smoke на реальной тестовой структуре;
- после QA включить для остальных tenant.

## 9. Тестирование

### Backend unit

- классификация явного audience-intent;
- приоритет детерминированных связей;
- отсутствие выдуманных кандидатов;
- отсутствие PII в LLM payload;
- human-readable статусы;
- fallback при недоступном LLM.

### Backend integration

- два tenant с одноимёнными отделами не смешиваются;
- чужой `course_id` возвращает `404`;
- черновик получает рекомендацию, но не `assignment_url`;
- опубликованный курс получает корректный URL;
- существующие назначения считаются без дублей;
- запрос не создаёт и не изменяет `Enrollment`, правила и cohorts.

### Frontend

- карточка для draft, review и published;
- быстрый вопрос отправляет явный intent;
- внутренние коды не отображаются;
- ссылка ведёт на `/assignments` с выбранным курсом;
- отсутствуют кнопки «Назначить», «Применить аудиторию» и скрытые write-вызовы;
- длинные названия отделов и должностей не ломают панель;
- клавиатура, focus trap, screen reader и mobile layout.

### Production smoke

1. Открыть черновик тестового курса.
2. Спросить «Кому назначить этот курс?».
3. Сверить названия и количества с экраном структуры.
4. Убедиться, что БД не получила новых назначений и правил.
5. Опубликовать отдельный тестовый курс штатным процессом.
6. Повторить вопрос и проверить только переход на экран назначения.
7. Закончить smoke без нажатия финальной кнопки назначения.

## 10. Критерии приёмки

- Помощник отвечает на вопрос об аудитории по реальной структуре tenant.
- Все рекомендуемые сущности существуют в текущем tenant.
- Для каждого вывода видна понятная причина.
- Численность совпадает с источником структуры.
- Ответ не содержит внутренних кодов и полей БД.
- Черновик можно анализировать, но нельзя назначить.
- Ни один запрос AI-помощника не изменяет назначения, правила, группы или
  сотрудников.
- Финальное назначение выполняется только методологом на `/assignments`.
- Backend, frontend и production smoke проходят без cross-tenant утечки и
  дублей.
