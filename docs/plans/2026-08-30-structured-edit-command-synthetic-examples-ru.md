# Спецификация синтетических примеров структурированных команд редактирования (Step 2)

**Статус:** спецификация-пример для контракта Step 2 «Structured edit command
and patch contract» корневого плана
[`2026-08-30-contextual-ai-editor-and-generation-quality-plan.md`](2026-08-30-contextual-ai-editor-and-generation-quality-plan.md).

**Дата:** 2026-08-30

**Назначение:** показать на синтетических сценариях, как обычные запросы
HR/методолога отображаются в нормализованную команду контракта Step 2:
нормализованное намерение (intent), выбранную цель, ограничения, базовую
версию, типизированные операции патча, ссылки на источники, результат
проверки применимости и ожидаемое поведение предпросмотра. Все имена, тексты
и содержимое — синтетические. Реальные данные клиентов не включены.

**Границы документа:** документ не предписывает нерешённые продуктовые решения
(доступность экрана по ролям помимо `methodologist`, поведение согласия на
аналитику, сроки хранения, модель undo). Он не изменяет корневой план и
UX-спецификацию
[`2026-08-30-ai-editor-methodologist-ux-spec-ru.md`](2026-08-30-ai-editor-methodologist-ux-spec-ru.md),
а иллюстрирует их на уровне контракта.

## 1. Схема разбора запроса

Каждый синтетический сценарий ниже разложен по одним и тем же полям контракта
Step 2:

| Поле | Смысл |
|---|---|
| **Запрос методолога** | Свободная формулировка обычным русским языком (синтетическая) |
| **Intent (нормализованный)** | Категория из таксономии корневого плана |
| **Selected target** | Тип и путь цели (`course`, `module`, `lesson`, `quiz`, `question`, `answer_option`, `explanation`) |
| **Constraints** | Ограничения операции, например `preserve_correct_answer` |
| **Base version** | Версия контента, к которой привязан предпросмотр |
| **Patch operations** | Типизированные операции структурного патча |
| **Source evidence** | Ссылки на фрагменты разрешённых источников |
| **Validation / applicability** | Результат детерминированной проверки и статус применимости |
| **Expected preview** | Ожидаемое поведение предпросмотра без мутации контента |

Базовое синтетическое окружение для всех сценариев:

- курс: «Охрана труда для офиса» (синтетический);
- урок 1.2: «Электробезопасность»;
- тест урока, вопрос 3 из 5: «Какой документ регламентирует проверку
  удлинителей?» с четырьмя вариантами А–Г;
- связанный источник: документ «Правила работы с электрооборудованием
  (образец)», раздел 4 (синтетический);
- actor: авторизованный `methodologist` тенанта; tenant и actor выводятся
  сервером из аутентифицированного контекста;
- локаль: `ru`.

## 2. Сценарий 1 — переписать формулировку (rewrite wording)

- **Запрос:** «Переформулируй вопрос проще, чтобы понял новый сотрудник».
- **Intent:** `rewrite_wording`.
- **Selected target:** `question` — «Курс → Модуль 1 → Урок 1.2 → Тест →
  Вопрос 3».
- **Constraints:** `preserve_correct_answer`; `preserve_question_type`;
  `preserve_score`.
- **Base version:** черновая версия `draft-12` вопроса 3 (синтетический
  идентификатор).
- **Patch operations:**
  - `update_field { entity: question, field: text, from: <текущий текст>,
    to: <упрощённая формулировка> }`.
- **Source evidence:** отсутствует — операция меняет только стиль; блок
  источников в предпросмотре скрыт.
- **Validation / applicability:** вопрос синтаксически полон; переноса факта
  между вариантами нет. Статус: `applicable`; некритичных предупреждений нет.
- **Expected preview:** before/after двухколоночный; подсветка изменённого
  поля `text`; кнопка «Применить» доступна; apply требует текущей base
  version и явного подтверждения; сама операция preview контент не меняет.

## 3. Сценарий 2 — добавить контекст (add context)

- **Запрос:** «Добавь в вопрос рабочую ситуацию: сотрудник подключает
  удлинитель на складе».
- **Intent:** `add_context`.
- **Selected target:** `question` — вопрос 3.
- **Constraints:** `preserve_correct_answer`; `preserve_answer_options`;
  `grounded_in_source`.
- **Base version:** `draft-12`.
- **Patch operations:**
  - `update_field { entity: question, field: text, operation: prepend,
    to: <вводная фраза-сценарий> }`.
- **Source evidence:** фрагмент «Правила работы с электрооборудованием
  (образец)», раздел 4 — только если вводная фраза подтверждается источником.
  Если источника для добавляемой детали нет — см. частичное выполнение ниже.
- **Validation / applicability:** если добавленный контекст не подтверждается
  ни источником, ни текущим текстом урока — предупреждение
  `unsupported_correct_answer`-семантики для добавляемого утверждения; статус
  `applicable_with_warnings` либо `not_applicable` при критичности.
- **Expected preview:** новая вводная фраза подсвечена как добавленная;
  источники показаны разворачиваемыми фрагментами; при частичном выполнении
  предпросмотр прямо называет, что выполнено, а что нет.

## 4. Сценарий 3 — перегенерировать дистракторы (regenerate distractors)

- **Запрос:** «Сделай неверные варианты менее очевидными, но оставь правильный
  ответ как есть».
- **Intent:** `regenerate_distractors`.
- **Selected target:** `question` — вопрос 3.
- **Constraints:** `preserve_correct_answer` (обязательное, применяется
  сервером); `preserve_question_type`; `preserve_score`; `refutable_from_source`.
- **Base version:** `draft-12`.
- **Patch operations:**
  - `replace_collection { entity: question, field: answer_options, scope:
    distractors_only, items: [<новые Б, В, Г с моделью заблуждения каждой>] }`.
- **Source evidence:** по одному фрагменту источника на каждый дистрактор,
  подтверждающему его опровержимость; если у дистрактора подтверждения нет —
  предупреждение `implausible_distractors`.
- **Validation / applicability:** проверка, что `preserve_correct_answer` не
  нарушен патчем (поле correct_answer отсутствует в операциях — нарушение
  контракта схемы блокирует применимость до валидатора); проверка
  неповторяемости дистракторов и отсутствия абсурдных вариантов. Статус:
  `applicable` при чистой проверке.
- **Expected preview:** подсвечены только варианты Б–Г; правильный вариант А
  показан неизменным; блок источников раскрывается по каждому дистрактору;
  apply невозможен без подтверждения и неизменённой base version.

## 5. Сценарий 4 — выровнять длину ответов (balance answer length)

- **Запрос:** «Вариант А заметно длиннее остальных — сделай все варианты
  похожими по подробности».
- **Intent:** `balance_answer_length`.
- **Selected target:** `question` — вопрос 3.
- **Constraints:** `preserve_correct_answer`; `preserve_semantics`; правило
  эвристики: длина каждого дистрактора в пределах порога относительно
  правильного ответа (пороги версионированы, из корневого плана).
- **Base version:** `draft-12`.
- **Patch operations:**
  - `update_field { entity: answer_option, id: <Б>, field: text, to: … }` —
    и аналогичные операции для остальных затронутых вариантов (в обе стороны:
    и сокращение правильного при необходимости не выполняется без явного
    разрешения — по умолчанию правятся только дистракторы).
- **Source evidence:** обычно отсутствует (операция стилистическая); если
  дистракторы перезаписываются с опорой на источник — фрагменты показываются.
- **Validation / applicability:** проверка снимает предупреждение
  `correct_answer_length_signal`; если после выравнивания два варианта
  становятся равно-правдоподобными — критичное предупреждение
  `multiple_plausible_correct_answers`, статус `not_applicable`.
- **Expected preview:** подсветка изменённых полей вариантов; краткая сводка
  проверки «Проверка пройдена» либо блокирующий список с кнопкой «Изменить
  запрос».

## 6. Сценарий 5 — конфликт устаревшей версии (stale-version conflict)

- **Запрос:** «Упрости пояснение к вопросу 3».
- **Intent:** `add_or_rewrite_explanation` (в данном сценарии важно поведение
  версий, а не категория).
- **Selected target:** `explanation` — пояснение к вопросу 3.
- **Constraints:** `preserve_correct_answer`.
- **Base version:** `draft-12`.
- **Patch operations:**
  - `update_field { entity: explanation, field: text, from: <текущий>,
    to: <упрощённый> }`.
- **Source evidence:** отсутствует (стилистическая операция).
- **Validation / applicability:** патч валиден относительно `draft-12`, но к
  моменту apply содержимое уже перезаписано другой правкой, и текущая версия
  стала `draft-13`. Apply отклоняется: optimistic concurrency; предпросмотр
  помечается `stale` и подлежит регенерации против текущей версии.
- **Expected preview:** сам предпросмотр отображается как обычно; при нажатии
  «Применить» — отказ без мутации и понятное сообщение о том, что текст
  изменился с момента предпросмотра, с предложением запросить предложение
  заново. Содержимое чужой правки в сообщении не раскрывается.

## 7. Сценарий 6 — запрос вне границ (out-of-scope request)

- **Запрос:** «Снизь порог прохождения теста и заодно поправь вопрос 3».
- **Intent:** нормализация невозможна в рамках полномочий ассистента —
  категория `other` с явным отказом; патч не формируется.
- **Selected target:** запрос затрагивает настройки теста (вне полномочий) и
  вопрос 3 (в полномочиях).
- **Constraints:** — (не применимо; патч не создаётся).
- **Base version:** не фиксируется, так как предпросмотр не создаётся.
- **Patch operations:** отсутствуют.
- **Source evidence:** отсутствует.
- **Validation / applicability:** статус `rejected_out_of_scope`; ассистент
  объясняет границу полномочий (настройки теста, другой урок, другой курс,
  удаление правильного ответа) и предлагает переформулировать запрос к
  выбранному вопросу.
- **Expected preview:** предпросмотр не показывается; реакция — вежливый
  отказ с альтернативой, без частичного патча к вопросу 3 (частичное
  выполнение здесь не применяется, чтобы не уводить методолога от явного
  выбора цели).

## 8. Сценарий 7 — опубликованный курс: требование черновой версии

- **Запрос:** «Добавь контекст к вопросу 3» — при том, что курс
  «Охрана труда для офиса» уже опубликован.
- **Intent:** `add_context`.
- **Selected target:** `question` — вопрос 3; бейдж цели: «опубликован —
  правки создадут новую версию».
- **Constraints:** `preserve_correct_answer`; `published_version_immutable`.
- **Base version:** опубликованная версия `published-3` (синтетический
  идентификатор); apply не может изменять её in place.
- **Patch operations:**
  - `create_draft_revision { from: published-3, changes: [update_field {
    entity: question, field: text, operation: prepend, to: … }] }`.
- **Source evidence:** фрагмент источника, на котором основана вводная фраза.
- **Validation / applicability:** проверка валидности патча и того, что
  target-версия действительно опубликована; статус `applicable` с
  обязательным подтверждением создания черновой версии перед apply.
- **Expected preview:** before/after как обычно; подпись, к какой версии
  применяется изменение; при apply — диалог подтверждения создания черновой
  версии; сотрудники, начавшие курс ранее, остаются на `published-3`;
  назначенные на неё прогресс и результаты не меняются.

## 9. Сценарий 8 — намеренный новый запрос (intentional new request)

- **Запрос:** методолог дважды подряд отправляет один и тот же текст
  «Сделай неверные варианты менее очевидными, но оставь правильный ответ как
  есть» к той же цели и той же base version — каждый раз как осознанное
  новое действие, а не как повторная отправка при сбое транспорта.
- **Intent:** `regenerate_distractors` (оба раза).
- **Selected target:** `question` — вопрос 3.
- **Constraints:** идентичны первому запросу.
- **Base version:** `draft-12` (не изменилась между запросами).
- **Patch operations:** тип операций идентичен сценарию 3; каждый
  намеренный новый запрос несёт новый idempotency key и создаёт новый
  request с собственным request identifier и жизненным циклом (событие
  `regenerated`/`requested`), а не переиспользует первый.
- **Source evidence:** идентичен сценарию 3.
- **Validation / applicability:** оба предложения существуют параллельно;
  применён может быть любой, второе применение к той же base version после
  первого apply отклоняется как stale. Метрика повторного запроса одной
  категории к одной цели фиксируется как сигнал продукта.
- **Expected preview:** каждый предпросмотр самодостаточен; параллельные
  предпросмотры не мутируют контент; кнопка «Другой вариант» эквивалентна
  такому повтору по контракту.
- **Отличие от транспортного повтора:** намеренный новый запрос (новый
  idempotency key) и повторная отправка того же запроса при сбое сети
  (тот же стабильный idempotency key и идентичная нормализованная
  нагрузка) — разные ситуации; вторая описана в сценарии 9 и не создаёт
  вторую цепочку жизненного цикла.

## 10. Сценарий 9 — идемпотентность: повтор и коллизия (retry and collision)

- **Запрос:** методолог нажимает «Применить» к одному и тому же подтверждённому
  предложению дважды (например, из-за повторной отправки при медленной сети).
  Тот же принцип действует для повторной отправки запроса/предпросмотра при
  транспортном сбое: тот же стабильный idempotency key и идентичная
  нормализованная нагрузка.
- **Intent:** `balance_answer_length` (для определённости; поведение общее для
  всех категорий).
- **Selected target:** `question` — вопрос 3.
- **Constraints:** `preserve_correct_answer`.
- **Base version:** `draft-12`.
- **Patch operations:** набор операций первого apply.
- **Source evidence:** без изменений.
- **Validation / applicability:**
  - apply идемпотентен по паре `(request identifier, base version)`:
    повторная команда apply с тем же request identifier и той же base
    version не создаёт вторую ревизию и не дублирует правку; результат
    первого apply возвращается как итог;
  - повтор create-команды запроса/предпросмотра (transport retry или
    повторная отправка формы) возвращает идентификаторы исходных request и
    предпросмотра; вторая цепочка жизненного цикла и второе выполнение
    провайдера не создаются;
  - тот же idempotency key с другой целью, инструкцией, ограничениями,
    base version или нормализованной нагрузкой — коллизия идемпотентности:
    запрос отклоняется fail-closed (без создания request, предпросмотра
    или мутации);
  - идемпотентность apply отдельна от идемпотентности request/preview и не
    покрывает её.
- **Expected preview:** после первого успешного apply повторный вызов
  возвращает подтверждение уже применённого состояния, прочитанное из
  хранилища (не из локального состояния), без второй ревизии; кнопка
  «Отменить последнее изменение» доступна в контракте undo (модель undo —
  отдельное решение, здесь не назначается). При повторе создания
  предпросмотра возвращается исходный предпросмотр, а не новый.

## 12. Общие инварианты сценариев

1. Preview не мутирует контент ни в одном сценарии.
2. Apply выполняется только при неизменённой base version и явном
   подтверждении; apply идемпотентен по паре `(request identifier,
   base version)`.
3. Идемпотентность request/preview отдельна от идемпотентности apply:
   намеренный новый запрос несёт новый idempotency key и создаёт новую
   цепочку; повторная отправка с тем же стабильным idempotency key и
   идентичной нормализованной нагрузкой возвращает исходные request и
   предпросмотр без второй цепочки и без второго выполнения провайдера;
   тот же key с другой целью, инструкцией, ограничениями, base version
   или нагрузкой отклоняется как коллизия (fail-closed).
4. Патч не выходит за пределы выбранной сущности; constraint
   `preserve_correct_answer` проверяется сервером.
5. Ссылки на источники показываются только там, где операция опирается на
   источник; иначе блок источников скрыт.
6. Опубликованная версия не изменяется in place — создаётся новая черновая
   ревизия; обучающиеся остаются на своей версии.
7. Все тексты запросов и содержимое в этом документе синтетические; в
   аналитическом контуре используются только нормализованные категории и
   статусы, а не тексты инструкций.
