## 1. Цель и не-цели

### 1.1. Цель

Определить закрытый синтетический корпус кейсов и детерминированный протокол
скоринга для ассистента методолога, который предлагает правки одиночных
вопросов с одним правильным ответом (single-correct MCQ). Корпус должен:

- покрывать **каждую** метку из `EditorQualityIssueLabel`
  (`apps/api/app/modules/editor_assistant/taxonomy.py`, строки 32–45):
  `correct_answer_length_signal`, `correct_answer_style_signal`,
  `implausible_distractors`, `multiple_plausible_correct_answers`,
  `unsupported_correct_answer`, `malformed_question`,
  `duplicate_question`, `rote_recall_only`,
  `language_or_translation_problem`, `explanation_leaked_into_answer`,
  `other`;
- быть напрямую исполнимым последующим тест-агентом без доработок
  исходников: ожидания кейсов формулируются в терминах входов и выходов
  существующих контрактов `question_validator.py`, `patch_contract.py` и
  `schemas.py`;
- полностью состоять из синтетического контента: имена, компании, email,
  реальные документы, секреты и данные арендаторов запрещены.

### 1.2. Не-цели

- Не менять код, тесты, миграции, `AGENTS.md`, `VERSION`, `CHANGELOG`.
- Не измерять и не утверждать фактических метрик текущего рантайма:
  все пороги в этом документе — **предложение**, подлежащее подтверждению
  прогоном.
- Не заменять ручную методологическую приёмку: корпус оценивает
  детерминированные и модельные сигналы качества, а не педагогическую
  ценность курса.
- Не покрывать multi-answer, True/False, open-ended и кластерные форматы
  вопросов — только single-correct MCQ (инвариант «ровно один правильный
  ответ» закреплён в `schemas.py`: `EditorAssistantPatchOperation` требует
  `sum(before_correct) == 1` и сохранение текста правильного ответа).
- Не создавать параллельные канонические документы: результаты после
  выполнения переносятся в существующие канонические файлы, временный план
  удаляется.

## 4. Корпус: 26 кейс-ID (27 исполняемых сценариев)

### 4.1. Правила построения

- Все факты вымышлены, нейтральны по тематике (канцелярия, склад, календарь,
  география времени, правила внутреннего распорядка вымышленной организации
  без имени). Никаких имён, компаний, email, реальных документов, секретов,
  tenant-данных.
- Идентификаторы вариантов: стабильные `choice_id` вида
  `c1`, `c2`, `c3`, `c4` — фиксированы для кейса; `is_correct` указан явно.
- `question_id` — синтетические коды вида `q-<категория>-<nn>`,
  удовлетворяющие `_OPAQUE_CODE_RE` валидатора.
- Ожидания сформулированы в терминах
  `validate_question_set(QuestionSet(...), ValidatorConfig(...))` →
  `(status, {f.code})` и, для patch-уровня, контрактов `schemas.py`.
- Для модельных кейсов (категория 11: `q-oth-01`, `q-oth-02`, `q-oth-03`)
  ожидание помечено как «модельное» — оно проверяется протоколом §5.1 как
  bounded oracle, а не чистым валидатором.

Легенда полей кейса: **id / язык / синтетические исходные факты / вопрос,
варианты (choice_id, текст, is_correct), объяснение / ожидаемые коды /
blocking-ожидание / допустимые интенты (`EditorIntent`, HTTP-уровень) /
запрещённые смысловые изменения.**

### 4.1.1. Правило допустимых интентов (публичный контракт)

Во всех кейсах поле `allowed_intents` использует **только** девять
публичных значений `EditorIntent` из `schemas.py`:

`rewrite_wording`, `simplify_language`, `add_context`,
`regenerate_distractors`, `balance_answer_length`, `change_difficulty`,
`make_scenario_based`, `add_or_rewrite_explanation`,
`fix_source_grounding`.

Значения `EditorIntentCategory` из `taxonomy.py`, не имеющие публичного
HTTP-эквивалента (`fix_multiple_correct_answers`, `remove_duplication`,
`fix_grammar`, `split_or_merge_content`, `other`), в `allowed_intents`
кейсов не используются. Они являются taxonomy-only категориями внутренней
аналитики (`intent_category` запроса) и описываются в кейсах отдельным
полем `taxonomy_only_intent_note` (не-HTTP, только для внутренней
разметки); на поведение фикстур они не влияют.

## 5. Скоринг: метрики

### 5.1. False positive / false negative по каждой метке

Для каждой метки `L ∈ EditorQualityIssueLabel` на корпусе §4:

- `TP(L)` — кейсы с ожиданием `L`, где найден `L`;
- `FP(L)` — кейсы, где найден `L`, хотя `L` не входит в ожидания кейса
  (включая негативы с пустым множеством ожиданий): неожиданно найденный
  код — это FP для метки найденного кода;
- `FN(L)` — кейсы с ожиданием `L`, где `L` не найден: пропущенный
  ожидаемый код — это FN для метки ожидаемого кода.

Метрики на метку:

- `precision(L) = TP / (TP + FP)`, `recall(L) = TP / (TP + FN)`;
- сводный micro-F1 по всем меткам; негативные кейсы дают
  specificity = TN / (TN + FP).

Граница применимости: детерминированный FN/FP-скоринг считается **только
по десяти меткам, проверяемым валидатором** (`correct_answer_length_signal`
… `explanation_leaked_into_answer`, кроме `other`). Метка `other` в
детерминированный скоринг не входит: у неё нет детерминированного
сигнала в `validate_question_set`. Она определяется как отдельный
**модельный bounded oracle**: для `q-oth-03` ожидается необязательная
модельная пометка `other` (binary hit/miss, отчёт отдельно от
precision/recall детерминированных меток); для негативов `q-oth-01/02`
модельная пометка `other` трактуется как model-level FP, но не влияет на
детерминированный micro-F1.

Требование детерминизма: `validate_question_set` при фиксированном корпусе
должен давать бит-в-бит одинаковый результат. Ожидания кейсов §4
**PARTIALLY VERIFIED** статическим сопоставлением с текущим кодом
валидатора; фактическое исполнение и наблюдаемые FP/FN остаются **NOT
VERIFIED**. При будущем прогоне FP/FN для детерминированных категорий
(§4.2–4.11) обязаны быть нулевыми. Для модельных ожиданий
(bounded oracle `other`) допускаются вероятностные ошибки, но они
фиксируются в отчёте отдельно.
Допустимые нецелевые коды (true positives по сопутствующему сигналу,
включены в ожидания кейса): `q-imp-01` дополнительно ожидает
`correct_answer_length_signal`. Появление любого иного кода — FP для
этой метки; отсутствие ожидаемого кода — FN. Оба — провал кейса.
Сопутствующий код, ранее заявленный для `q-dup-01`
(`correct_answer_length_signal` на обоих вопросах), исключён из
ожиданий: пара редизайнирована с дословно одинаковым промптом и
выровненными длинами вариантов (все по 2 токена), единственное ожидание
кейса — `duplicate_question`.

### 5.1.1. Правило вычисления blocking-ожиданий

Blocking- и status-ожидания кейсов не задаются «по категории»; каждое
ожидание в §4 выведено для **явной** конфигурации `ValidatorConfig()` (все
пороги по умолчанию, `enabled_issue_codes` = все метки) и **полного**
состава `QuestionSet` кейса. Правила вывода:

1. одиночная находка без `blocking=True` в коде валидатора →
   `status = WARN`, blocking = false;
2. находка с `blocking=True` (structural, duplicate, unsupported, leak,
   multiple-plausible) → `status = FAIL`, blocking = true;
3. квиз-уровневые ветви `correct_answer_length_signal` (обе — source-derived
   expectations для указанного `ValidatorConfig()`; literal execution
   остаётся **NOT VERIFIED**):
   - ветвь доли: `correct_longest_share > longest_answer_block_share`
     (0.50) при `eligible ≥ min_quiz_sample_size` (4) → blocking;
   - ветвь baseline «choose-longest»: `longest_answer_accuracy ≥
     choose_longest_pass_score` (0.80) при `eligible ≥ 4` → blocking;
   - при `longest_answer_warn_share < share ≤ 0.50` — только warning;
4. состав `QuestionSet` меняет результат (например, один вопрос с длиной
   в наборе из 4 не достигает ни одной квиз-ветви) — поэтому fixture
   хранит полный список вопросов, а не одну «дефектную» строку;
   переиспользование кейса в другом QuestionSet требует пересчёта
   ожиданий по этим правилам, а не копирования blocking из таблицы.

### 5.2. Сохранение семантики

- Каждый patch (`StructuredEditPatch` из `patch_contract.py`) оценивается:
  допустимы только операции в рамках `target.selected_scope` и
  `operation_constraints.allowed_field_paths`;
- изменения затрагивают только `question.text`, `question.answer_options`,
  `question.explanation` (`EditorPatchPath`);
- бинарная метка `semantic_preserved` на кейс: экспертная (fixture) пометка
  «что должно остаться неизменным» из поля «запрещено» сверяется с
  after_value операций. Автоматическая часть: правильный вариант
  (identity и текст) и `choice_id` не меняются — см. 5.3.

### 5.3. Стабильность идентификаторов вариантов

- Множество `choice_id` до и после правки совпадает, порядок сохранён
  (инвариант `schemas.py`: `before_ids == after_ids`);
- ни одна правка не добавляет/не удаляет варианты через
  `EditorAssistantPatchOperation` (операция `replace` для
  `question.answer_options` допускает изменение только текстов
  дистракторов);
- метрика: `choice_id_stability = доля кейсов с полным совпадением
  множества и порядка id` — целевое значение 1.0.

### 5.4. Идентичность правильного ответа

- Инвариант `schemas.py`: текст и позиция `is_correct = true` не
  изменяются (`before[correct_index].text == after[correct_index].text`);
- метрика `correct_identity_preserved = 1.0` обязательна для всех кейсов,
  где правильный ответ корректен по fixture;
- для категорий, где правильный ответ сам дефектен (`q-uns-01/02`),
  ожидается отсутствие apply-патча (blocking) — попытка «пересадить»
  правильный ответ считается провалом кейса;
- сценарий `q-len-03 (control)` — **валидный patch-control** по спецификации
  фикстуры: тексты правильных ответов всех четырёх вопросов совпадают со
  сценарием broken байт-в-байт; literal execution остаётся **NOT VERIFIED**,
  а правка затрагивает только
  тексты дистракторов, поэтому сценарий включается в
  patch-preservation scoring наравце с остальными кейсами.

### 5.5. Опора на источник (source grounding)

- Каждый `COMPLETED` preview обязан содержать ≥ 1
  `EditorAssistantSourceReference` (`source.source_reference_count ≥ 1`,
  `schemas.py`);
- для кейсов с `require_source_evidence = true` в
  `OperationConstraints` отсутствие evidence — провал;
- метрика `groundedness = доля completed-превью с непустым и
  уникальным набором source_id`; **blocking-порог = 1.0**: для
  синтетического корпуса исходные факты полны и детерминированы, поэтому
  любое completed-превью без опоры — дефект кейса или ассистента, а не
  статистический шум;
- anti-hallucination: `source_id` должны ссылаться на synthetic fixture
  documents; обращение к несуществующему `source_id` — провал.

### 5.6. Языковая консистентность ru/kk

- Ответ ассистента должен быть на языке кейса: для `ru` — кириллица без
  казахских специфичных букв; для `kk` — наличие ≥ 1 буквы из
  `KAZAKH_CYRILLIC_EXTRA` в связных фрагментах и отсутствие служебных
  русских вставок, не присутствовавших в источнике (консервативная
  проверка по образцу `source_analysis.py`);
- смешанные кейсы `q-lng-01/02` оцениваются по ожиданию «после правки
  язык однороден в рамках locale кейса»;
- метрика `language_consistency = доля кейсов, где язык всех after-значений
  соответствует locale` — целевое значение 1.0.

### 5.7. Latency и fallback

- `duration_ms` — единственная разрешённая телеметрия длительности
  (`analytics.py`, `EVENT_METADATA_ALLOWLIST`);
- на корпусе фиксируются: p50/p95/p99 `duration_ms` по кейсу, доля
  `PREVIEW_FAILED` с `reason_code ∈ {provider_timeout,
  provider_error}`, доля успешных fallback-повторов (`attempt ≥ 2`);
- абсолютные целевые значения latency в этом документе не утверждаются
  (нет измерений рантайма); протокол требует лишь, чтобы p95
  фиксировался и регрессия относительно предыдущего прогона того же
  корпуса была ≤ 20 %.

## 6. Протокол прогона

1. Собрать `QuestionSet` из фикстур кейса; прогнать
   `validate_question_set` для базового состояния (до правки) и
   зафиксировать ожидаемые коды §4.
2. Смоделировать (unit) или выполнить (integration) preview через
   `PreviewIdempotencyGuard.preview` с фиктивным `EditPatchProvider`,
   возвращающим заранее записанный `StructuredEditPatch` для каждого кейса.
3. Применить проверки §5.2–5.6 к патчу и §5.7 — к телеметрии.
4. Для blocking-кейсов убедиться, что `ValidationReport.status == FAIL`;
   в этом состоянии патч не проходит `_validate_patch_against_command`
   (`patch_contract.py`: `raise PatchContractError("Editor patch failed
   deterministic validation")`) — apply невозможен **безусловно**:
   ни `new_draft_revision_id`, ни override-поток, ни ручная пометка
   «применить» не обходят FAIL (draft-статус и `REQUIRES_NEW_DRAFT_REVISION`
   относятся к lifecycle снапшота, а не к обходу валидации).
5. Сформировать отчёт: таблица FP/FN по меткам + метрики §5 + сырые
   `project_patch_analytics` (только нормализованные поля).

## 7. Детерминированные пороги приёмки и предложение release gate

### 7.1. Пороги приёмки (детерминированные)

| Метрика | Порог |
|---|---|

| FN у любой метки на её же категориях (§4.2–4.11) | 0 |
| `choice_id_stability` | = 1.0 |
| `correct_identity_preserved` | = 1.0 |
| `groundedness` | = 1.0 (blocking) |
| `semantic_preserved` (по «запрещено» фикстур) | ≥ 0.95 |
| `language_consistency` | = 1.0 |
| blocking-кейсы: статус валидатора | FAIL у 100 % |
| warning-кейсы: статус | WARN (не FAIL) у 100 % |
| p95 latency регрессия | ≤ 20 % относительно предыдущего прогона |

### 7.2. Release gate (предложение)

- Gate добавляется в набор проверок релиза как unit/integration job:
  прогон корпуса + сравнение с предыдущим артефактом прогона
  (fingerprint: sha256 корпуса + версии `validator_version`,
  `prompt_version`, `generator_version`).
- Gate блокирует релиз при: любом нарушении порогов §7.1; изменении
  набора `EditorQualityIssueLabel` без обновлённого корпуса; появлении в
  event metadata любого ключа вне `EVENT_METADATA_ALLOWLIST`. Request
  analytics, patch analytics и test artifacts проверяются каждый по своей
  публичной projection/schema, а не по event metadata allowlist.
- Gate НЕ заменяет ручную продуктовую приёмку UI-флоу методолога.
- Статус gate: proposed — не заявлять, что он уже действует в CI, пока
  не будет фактически подключён отдельной задачей.

## 8. Контракт приватности и логирования

Обязательные правила (выведены из `analytics.py`, `patch_contract.py` и
`schemas.py`):

1. Во все telemetry/analytics projections и test artifacts **запрещено**
   записывать: текст инструкции, текст вопроса/вариантов/объяснения, source
   text, сырой ответ провайдера и `instruction_text`. Дополнительно event
   metadata не может содержать ключи вне `EVENT_METADATA_ALLOWLIST`;
   request analytics, patch analytics и test artifacts ограничиваются
   собственными публичными projection/schema.
2. Разрешено сохранять **в метаданных события** (`metadata_json`,
   `validate_event_metadata`) ровно 8 ключей: `issue_labels`,
   `duration_ms`, `attempt`, `generator_version`, `prompt_version`,
   `model_id`, `validator_version`, `reason_code`. Все значения этих
   ключей — ограниченные нормализованные коды, версии и числа
   (`model_id` — нормализованный код модели, а не сырой ответ
   провайдера); сырой контент ими не является и сохраняться не может.
3. Три отдельные схемы не смешивать:
   - **метаданные события** (`metadata_json`) — только 8 ключей из
     `EVENT_METADATA_ALLOWLIST` (`analytics.py`), проверяются
     `validate_event_metadata`;
   - **проекции запроса/события** (`analytics.py`) — `project_request`
     возвращает `intent_category`, `outcome_state` (`REQUEST_ANALYTICS_FIELDS`);
     `project_event` возвращает `event_type` (`EVENT_ANALYTICS_FIELDS`) +
     вложенный `metadata` из валидированных метаданных. `event_type`,
     `intent_category`, `outcome_state` — поля проекций, а не ключи
     `metadata_json`;
   - **patch analytics** (`patch_contract.py`) — `project_patch_analytics`
     возвращает свой набор: `target_entity_type`, `operation_count`,
     `source_reference_count`, `validation_status`, `applicability_status`,
     `content_lifecycle`, `provider`, `model_id`, `prompt_version`,
     `generator_version`, `validator_version`. Это поля патча, а не ключи
     метаданных события;
   - **test artifacts** — fixture/result schema §9.1 и fingerprint/result
     schema прогона; это тестовые поля, а не event metadata, request analytics
     или patch analytics.
4. Вместо сырых значений — хэши-отпечатки. Разрешены только:
   (а) sha256 нормализованного JSON-а payload по образцу
   `_request_payload_fingerprint` (`patch_contract.py`) — в пределах
   idempotency-механизма самого `patch_contract.py`; (б) отпечаток корпуса
   (sha256 списка `(case_id, content_hash)`), сохраняемый в тестовом
   артефакте прогона. Это не разрешение хранить произвольные хэши
   контента: тексты вопросов, вариантов, объяснений и source text не
   хешируются в telemetry/analytics и не сохраняются ни в каком виде.
5. Фикстуры корпуса хранятся только в репозитории, синтетические;
   выгрузка в analytics/telemetry любого кейс-контента запрещена.
6. Любое диагностическое сообщение должно быть из закрытых каталогов, а
   не свободным текстом: `schemas.py` — `_FAILURE_CONTRACTS`
   (`EditorAssistantFailureCode` → сообщение + `EditorApplicability`,
   доступ через `editor_assistant_failure_contract`) и `_ISSUE_MESSAGES`
   (`EditorValidationIssueCode`); `question_validator.py` —
   `_ISSUE_MESSAGES` (`EditorQualityIssueLabel`; конструктор
   `QuestionFinding` отвергает сообщение, не равное каталогу);
   `preview_use_case.py` — `_FAILURE_MESSAGES` (`PreviewUseCaseFailureCode`);
   `question_context.py` — `_FAILURE_MESSAGES` (`QuestionContextFailureCode`).

## 9. Конвертация корпуса в фикстуры (unit / integration / E2E)

### 9.1. Формат фикстур

- Один файл на категорию: `apps/api/tests/fixtures/editor_assistant/<category>.json`
  со схемой: `{synthetic, case_id, language, facts, question:{prompt,
  explanation, options:[{choice_id, text, is_correct}]}, signals,
  expected:{codes, status, blocking}, allowed_intents,
  taxonomy_only_intent_note, forbidden_semantic_changes}`;
  `synthetic: true` — обязательное поле каждой фикстуры (см. §9.3);
  `allowed_intents` — только значения `EditorIntent` из `schemas.py`.
- Идентификаторы: фикстуры для прямого исполнения валидатором используют
  компактные ID (`question_id` вида `q-<категория>-<nn>`, `choice_id`
  вида `c1`…`c4`), удовлетворяющие `_OPAQUE_CODE_RE` валидатора. Для
  HTTP/E2E-слоя каждый кейс дополнительно содержит детерминированное
  отображение в UUID: `question_uuid = uuid5(NAMESPACE, case_id)`,
  `choice_uuid = uuid5(NAMESPACE, f"{case_id}:{choice_id}")`; компактные
  ID фикстур и UUID транспортного слоя связаны только этим отображением,
  UUID-значения в сами кейсы не вписаны.

### 9.2. Уровни тестов

- **Unit (validator):** прямая сборка `QuestionSet`/`QuestionSignals` из
  фикстуры и проверка `(status, codes, blocking)` — покрывает §4.2–4.11
  без сети и провайдера.
- **Integration (service/patch):** фикстура превращается в
  `StructuredEditCommand` + заранее записанный провайдер; проверки scope,
  evidence, инвариантов `choice_id` и правильного ответа; телеметрия —
  только через `project_patch_analytics`.
- **E2E:** детерминированные UUID из §9.1 + сиды; сквозной запрос preview
  по синтетическому вопросу, созданному из фикстуры; ассерты на уровне
  контрактов `schemas.py`. Контент клиентов не используется нигде:
  E2E-данные создаются и удаляются в рамках прогона.

### 9.3. Правила без копирования клиентского контента

- Запрещено извлекать кейсы из production-БД, дампов, логов.
- Если захочется обогатить корпус реальными паттернами — сначала
  синтезировать эквивалентные конструкции вручную и зафиксировать
  синтетический статус в поле `facts`.
- Каждая фикстура содержит обязательное поле `synthetic: true` (в схеме
  §9.1), и проверку lint-типа, что в её строках нет email-подобных и
  телефоноподобных последовательностей.
