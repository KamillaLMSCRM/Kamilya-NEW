# План: завершение курса и возврат подписанного подтверждения

**Статус:** реализовано в feature-ветке; production release и живая приёмка ожидают отдельного разрешения
**Базовая версия:** `0.5.56`, SHA `371d86e6a094d114a83f9922dd3f3f9602736b9a`
**Область:** нативные курсы Kamilya LMS; SCORM и ЭЦП не входят в эту работу.

## 1. Цель

Сотрудник проходит весь курс и обязательные тесты в одном выделенном окне времени,
без ручного подтверждения каждого урока. После завершения курса он получает
персональный PDF с полноценным блоком ручной подписи, возвращает подписанный
PDF/фото непосредственно в Kamilya, а методист проверяет и принимает документ.
Tenant-администратор управляет текстом и реквизитами печатной формы. Принятый
скан входит в готовый evidence package как отдельный неизменяемый оригинал.

## 2. Инварианты

- Одно назначение имеет один общий таймер на курс и тестирование.
- Сервер по-прежнему не завершает курс, пока не посещены все уроки и не пройдены
  обязательные тесты.
- Посещение урока фиксируется автоматически действием «Следующий урок» либо
  успешной сдачей обязательного теста; отдельной кнопки подтверждения урока нет.
- Бумажный экземпляр относится только к событию завершения курса
  `procedure_type=training`, а не к отдельным урокам или тестам.
- Завершение курса, сертификат, OTP-подтверждение и бумажный экземпляр — разные
  факты; добавление скана не меняет оценку, попытки, сертификат или исходное событие.
- Все файлы и состояния tenant-scoped; связь с сотрудником, enrollment и release
  вычисляется сервером из исходного evidence event.
- Оригиналы сканов append-only. Замена добавляет новую запись, не перезаписывает
  предыдущую. Ручная подпись не называется ЭЦП.
- Истечение учебного окна после завершения курса не блокирует возврат документа.
- Superadmin impersonation не может добавлять, принимать или отклонять evidence.

## 3. Проверяемые интерфейсы — поверхности TDD

### A. Course player

- Кнопка «Отметить урок пройденным» отсутствует.
- «Следующий урок» атомарно сохраняет прогресс текущего урока и открывает следующий.
- Успешный обязательный тест сохраняет прогресс соответствующего урока.
- «Завершить курс» сохраняет последний урок и вызывает единое завершение курса.
- Ошибка сохранения прогресса не маскируется переходом на следующий урок.

### B. Learner evidence

- Обычный student-account и assignment-link student скачивают одинаковую
  персональную печатную форму своего course-completion event.
- Для `training`-события сотрудник может загрузить PDF/JPEG/PNG до 10 МБ.
- Assignment-link пользователь может работать только со своим exact enrollment.
- Upload создаёт `uploaded_pending_review`; повторная загрузка добавляет новую запись.

### C. Methodologist review

- Методист видит очередь `awaiting_return`, `uploaded_pending_review`, `accepted`,
  `replacement_requested`, `overdue`.
- Методист может безопасно открыть/скачать конкретный оригинал.
- `accept` и `request replacement` — отдельные аудируемые append-only решения;
  отклонение требует причины.
- Методист сохраняет резервную возможность прикрепить полученный вне LMS файл.

### D. Tenant template settings

- Tenant-admin настраивает заголовок, вводный текст, текст подтверждения, подписи
  сотрудника и представителя организации, подписи полей и примечание.
- Настройки валидируются, сохраняются в tenant settings и имеют PDF preview.
- При завершении курса в evidence event сохраняется снимок применённой версии
  формы, чтобы будущая смена настроек не меняла исторический документ.

### E. Evidence package

- Индивидуальный ZIP содержит основной PDF, manifest и все принятые подписанные
  оригиналы; manifest содержит filename, content type, size, SHA-256, uploader,
  upload/review timestamps и review outcome.
- До принятия скан не включается в готовый пакет, но остаётся доступен в очереди.
- PDF содержит полноценный печатный блок: ФИО, курс, версия, дата/результат,
  заявление, линии подписи сотрудника и представителя, даты и служебный ID.

## 4. Реализация вертикальными срезами

1. **Автоматический прогресс уроков.** RED web-тест → минимальная правка course
   player → GREEN → соседние quiz/navigation regression tests.
2. **Возврат скана сотрудником.** RED API tests на ownership/roles/state → learner
   upload/read endpoints → GREEN → RLS и assignment-link negatives.
3. **Проверка методистом.** RED tests на download/accept/replacement → review ledger
   и UI журнала → GREEN.
4. **Печатная форма и tenant-настройки.** RED renderer/settings tests → settings
   interface, snapshot и preview → GREEN → визуальный render PDF.
5. **Evidence package.** RED package/manifest tests → включение только принятых
   сканов → GREEN → hash/readback и deterministic export regression.
6. **Сборка.** API focused tests, web focused tests, typecheck, build, migration/RLS
   checks в одобренном Supabase DEV/test-контуре, Graphify AST update и анализ diff.
7. **Живая приёмка.** Только синтетический tenant: email learner и personal-link
   learner; download → print simulation → upload → review → accepted package.

## 5. Владение работой

| Владелец | Область записи |
|---|---|
| Root | этот план, архитектура, миграция, tenant settings, PDF/export package, интеграция, финальная проверка, Git/release |
| Luna A | только course-player frontend и его web tests |
| Luna B | только signed-scan backend lifecycle/routes/schemas/service и focused API tests |

Агенты не коммитят, не пушат, не деплоят, не читают секреты и не обращаются к
DEV/production. Общие файлы, миграция, каноническая документация и конфликты
остаются у root.

## 6. Приёмка и выпуск

Кандидат не считается готовым только по unit-тестам. Нужны: миграционный/RLS
readback, визуальная проверка PDF, открытие принятого скана методистом, проверка
пакета, две синтетические пользовательские траектории и negative-space проверки
ролей/tenant/enrollment. Production deployment не входит в этот план без отдельного
точного разрешения владельца на релиз конкретного SHA.
