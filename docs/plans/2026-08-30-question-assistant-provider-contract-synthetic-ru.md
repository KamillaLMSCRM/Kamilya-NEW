# Синтетическая спецификация провайдер-контракта предпросмотра одного вопроса (Шаг 4)

**Статус:** спецификация-пример для Шага 4 «Question assistant backend preview»
корневого плана
[`2026-08-30-contextual-ai-editor-and-generation-quality-plan.md`](2026-08-30-contextual-ai-editor-and-generation-quality-plan.md).

**Дата:** 2026-08-30

**Назначение:** показать на синтетических сценариях, как контракт провайдера
модели для предпросмотра одного вопроса связывает минимальный tenant-scoped
контекст (включая bounded raw-инструкцию и минимальное выбранное содержимое),
структурированный вход/выход, серверное ограничение `preserve_correct_answer`,
ссылки на источники без утечки аналитики, состояния
валидации/применимости, провенанс провайдера/модели/промпта, правила
отклонения результата и контролируемого fallback без ослабления валидации,
поведение устаревших версий, идемпотентные повторы и безопасные категории
ошибок. Все тексты, имена и содержимое — синтетические; данные клиентов не
включены.

**Границы документа:** документ не называет и не упорядочивает живых
провайдеров и не подменяет маршрутизацию — «approved model chain» из корневого
плана остаётся единственным источником порядка и не подтверждена здесь
конкретным провайдером. Документ не изменяет корневой план, спецификацию
примеров Step 2
[`2026-08-30-structured-edit-command-synthetic-examples-ru.md`](2026-08-30-structured-edit-command-synthetic-examples-ru.md)
и матрицу валидатора Step 3
[`2026-08-30-question-validator-synthetic-case-matrix-ru.md`](2026-08-30-question-validator-synthetic-case-matrix-ru.md),

## 1. Место контракта в шаге 4

Провайдер-контракт описывает один вызов предпросмотра: что получает провайдер
модели, что обязан вернуть, что проверяется сервером до и после вызова, и при
каких условиях результат становится применимым патчем.

Три границы контракта:

1. **До вызова провайдера** сервер собирает минимальный tenant-scoped контекст
   и нормализованную команду (контракт Step 2).
2. **Сам вызов** — неперсистентный запрос к провайдеру по утверждённому
   маршруту; провайдер не пишет в базу, не видит tenant identifiers и не
   получает данные за пределами минимального контекста.
3. **После вызова** сервер парсит структурированный ответ, прогоняет
   детерминированный валидатор (контракт Step 3) и только затем присваивает
   статус применимости.

Ключевое правило: провайдер никогда не является источником истины о
применимости, tenancy или correct answer — он предлагает, сервер решает.

## 2. Минимальный tenant-scoped контекст вызова

Провайдер получает только поля, необходимые для генерации патча выбранного
вопроса. Ничего сверх списка:

| Поле | Источник | Зачем провайдеру |
|---|---|---|
| `locale` | запрос методолога | языковая корректность текста |
| `target_entity_type` | нормализованная команда | тип цели (в Шаге 4 — `question`) |
| `selected_field_or_scope` | нормализованная команда | какие поля затрагивать |
| `operation_constraints` | нормализованная команда | например `preserve_correct_answer` |
| `base_snapshot` | серверный immutable snapshot на base version | неизменяемое содержимое вопроса и вариантов |
| `permitted_source_fragments` | серверно отфильтрованные разрешённые источники | опора и опровержимость |
| `normalized_intent` | серверная нормализация инструкции | ожидаемая форма ответа |
| `raw_instruction` | bounded raw-инструкция методолога | исполнение редактирования по замыслу автора |
| `instruction_digest` | серверный дайджест инструкции | идемпотентность повтора (не смысловая замена) |

Разрешено и обязательно передавать провайдеру (в рамках утверждённого
контракта обработки):

- **bounded raw-инструкция методолога** — исходный свободный текст команды в
  ограниченном виде: провайдер выполняет редактирование по замыслу автора, а
  не по утерянному при нормализации намерению. Дайджест (`instruction_digest`)
  служит только идемпотентности повтора и **не заменяет** raw-инструкцию;
- **минимальное выбранное содержимое вопроса/вариантов/свидетельств** —
  `base_snapshot` и `permitted_source_fragments`, строго ограниченные
  `selected_field_or_scope`.

Условие разрешения: эти tenant-scoped сырые поля входят **только в request
провайдера** по утверждённому контракту обработки. Они запрещены во всех
обычных каналах: логи, метрики и их label-ы, cross-tenant аналитика,
маркетинговая аналитика, сообщения об ошибках, провенанс-поля. Допустимая
граница — сам вызов провайдера; всё, что записывается сервером, кроме
неперсистентного запроса, оперирует только нормализованными полями
(раздел 5).

Запрещено передавать провайдеру:

- `tenant_id`, `actor_id`, email, телефон, имена пользователей — сервер
  подставляет их только в собственную телеметрию;
- содержимое других вопросов квиза за пределами контекста, требуемого
  операцией (для Шага 4 — за пределами выбранного вопроса);
- данные других tenant-ов и любые cross-tenant агрегаты.

Tenant и actor выводятся сервером из аутентифицированного контекста и служат
для авторизации и телеметрии, но не входят в payload провайдера.

## 3. Структурированный вход и выход

### 3.1 Вход провайдера (запрос)

Синтетическая схема (JSON-подобная, для иллюстрации):

```
{
  "contract_version": "1",
  "request_id": "<opaque server-generated id>",
  "normalized_intent": "regenerate_distractors",
  "target": { "entity": "question", "field_scope": ["answer_options"] },
  "constraints": ["preserve_correct_answer", "refutable_from_source"],
  "locale": "ru",
  "base_snapshot": {
    "question_text": "<синтетический текст>",
    "answer_options": ["<А>", "<Б>", "<В>", "<Г>"],
    "correct_index": 0,
    "explanation": "<синтетическое пояснение>"
  },
  "permitted_source_fragments": [
    { "fragment_id": "E01", "text": "<синтетический фрагмент>" }
  ],
  "raw_instruction": {
    "locale": "ru",
    "text": "<синтетический текст инструкции методолога>",
    "max_length": 8000
  },
  "instruction_digest": "<opaque digest>"
}
```

`raw_instruction` — bounded raw-инструкция: передаётся целиком, но с серверным
лимитом длины и без tenant/actor identifiers. `instruction_digest` остаётся
ключом идемпотентности и самостоятельной смысловой нагрузки не несёт.

### 3.2 Выход провайдера (ответ)

Провайдер обязан вернуть ровно один структурированный объект:

```
{
  "contract_version": "1",
  "patch": [
    {
      "op": "replace_collection",
      "entity": "question",
      "field": "answer_options",
      "scope": "distractors_only",
      "items": ["<новый Б>", "<новый В>", "<новый Г>"],
      "misconceptions": ["<модель заблуждения Б>", "…", "…"]
    }
  ],
  "summary": "<краткое человекочитаемое описание>",
  "source_evidence": [
    { "fragment_id": "E01", "supports": ["distractor:1"], "note": "<краткая привязка>" }
  },
  "provenance": {
    "provider_id": "<opaque provider id>",
    "model_id": "<opaque model id>",
    "prompt_id": "<prompt version id>"
  }
}
```

Ответ, который не парсится в эту схему, не содержит обязательных полей или
содержит операции вне `field_scope`, отклоняется целиком как
`provider_output_unparseable` — частичное применение запрещено.

### 3.3 Обязательные структурные поля генерации

Внутри патча для каждого затронутого элемента сохраняются структурные поля
контракта раздела 4 корневого плана: опора на фрагмент, атомарный факт,
модель заблуждения дистрактора, сложность. Пояснение не может быть вложено в
текст правильного ответа — это проверяется и схемой, и валидатором.

## 4. Серверное `preserve_correct_answer`

`preserve_correct_answer` enforced сервером, а не промптом:

1. Схема патча не содержит операций над полем correct answer, если constraint
   задан: попытка включить `correct_index`, текст правильного варианта или
   score в патч — contract violation, статус `not_applicable` до вызова
   валидатора.
2. После парсинга сервер сравнивает правильный вариант base snapshot с
   правильным вариантом, который дал бы патч: несовпадение — блокирующее
   нарушение.
3. Промпт может повторять ограничение, но его игнорирование моделью не
   является причиной ослабить проверку: любое нарушение — блокировка.

## 5. Ссылки на источники без утечки аналитики

- Патч ссылается только на `permitted_source_fragments` по `fragment_id`;
  ссылки на внешние или не переданные фрагменты отклоняются.
- `source_evidence` содержит идентификатор фрагмента и краткую привязку
  (`supports`), но не копии фрагментов и не производные от них аналитические
  вычисления.
- Телеметрия вызова содержит только нормализованные поля: intent, статус,
  версии, длительность, счётчики findings. Тексты фрагментов, тексты ответов,
  raw-инструкция, тексты патча и любые производные от них строки в телеметрии,
  логах, метриках (включая label-ы), cross-tenant и маркетинговой аналитике,
  сообщениях об ошибках и провенанс-полях запрещены (инварианты разделов 6.3
  и 8 корневого плана). Граница раздела 2 соблюдается: tenant-scoped сырые
  поля существуют только внутри request провайдера.
- Провайдер не получает tenant identifiers, поэтому его внутренние логики
  (если есть) не могут связать содержимое с tenant-ом.

## 6. Состояния валидации и применимости

После парсинга сервер прогоняет детерминированный валидатор Step 3 и
присваивает ровно один статус:

| Статус | Значение | Применимость |
|---|---|---|
| `applicable` | валидатор не нашёл блокирующих замечаний | apply разрешён после подтверждения |
| `applicable_with_warnings` | только неблокирующие предупреждения | apply разрешён, предупреждения показаны; отклонение/fallback не триггерятся |
| `not_applicable` | есть блокирующие замечания (blocking FAIL) | apply запрещён; отклонение результата; возможен контролируемый fallback (раздел 8.1) |
| `provider_output_unparseable` | ответ не соответствует схеме (malformed — blocking FAIL) | патча нет; отклонение; возможен контролируемый fallback (раздел 8.1) |
| `rejected_out_of_scope` | запрос вне полномочий ассистента | патча не создаётся |

Провенанс записывается рядом с результатом: provider, model, prompt version,
validator version, contract version. Результат нельзя перезаписать задним
числом другим прогоном.

## 7. Провенанс провайдера, модели и промпта

Каждый результат предпросмотра содержит неизменяемую запись:

- `provider_id` — непрозрачный идентификатор маршрута из утверждённой
  конфигурации; порядок и имена живых провайдеров в этом документе не
  фиксируются;
- `model_id` — фактическая модель, которая вернула ответ (может отличаться от
  первичного маршрута при fallback — см. раздел 8);
- `prompt_id` — версия шаблона промпта;
- `validator_version` и `thresholds_version` — из контракта Step 3;
- `contract_version` — версия самой схемы входа/выхода.

Провенанс не подменяется: результат, полученный на одной модели, не
переприсваивается другой, а fallback фиксируется как факт вызова.

## 8. Fallback без ослабления валидации

Fallback следует утверждённой цепочке маршрутизации; конкретный порядок живых
провайдеров в документе не называется и не предполагается (provider-order-
agnostic). Правила:

1. Fallback возможен после технического сбоя маршрута либо после полного
   отклонения результата текущего провайдера по закрытым blocking-основаниям
   раздела 8.1. Частично отклонённый результат не используется.
2. Неблокирующие предупреждения качества не запускают fallback. Blocking FAIL
   может передать тот же запрос следующему провайдеру только с полным повтором
   parser/scope/evidence/validator-гейтов; это не является обходом findings.
3. Fallback не меняет контракт: схема входа/выхода, серверные ограничения и
   валидатор идентичны для всех звеньев цепочки.
4. Применимый предпросмотр фиксирует фактические `provider` и `model_id` того
   провайдера, чей результат принят после всех гейтов.
5. Неявное понижение строгости — запрет: не существует конфигурации, в которой
   вторая попытка пропускает часть проверок. Тест на это правило входит в
   регрессию шага.

### 8.1 Отклонённый результат провайдера и контролируемый fallback

Отклонение результата и fallback различаются по причине и проходят одни и те
же гейты:

1. **Основания отклонения результата провайдера** (каждое — blocking FAIL):
   - malformed: ответ не парсится в схему раздела 3.2 или не содержит
     обязательных полей (`provider_output_unparseable`);
   - scope-escaping: операция затрагивает поля вне `selected_field_or_scope`;
   - нарушение `preserve_correct_answer`: патч изменяет правильный вариант,
     его индекс или score;
   - evidence-invalid: ссылки на фрагменты, не переданные в
     `permitted_source_fragments`, или unsupported-утверждения без опоры;
   - validator-blocked: детерминированный валидатор Step 3 вернул блокирующие
     findings.
2. **Контролируемый fallback**: любой результат из пункта 1 отклоняется
   целиком (частичное применение запрещено) и **может** запустить fallback к
   следующему провайдеру утверждённой цепочки — при условии, что следующий
   вызов проходит ровно те же гейты: тот же parser, те же scope-проверки, ту
   же evidence-проверку и тот же валидатор. Fallback никогда не ослабляет и
   не пропускает валидацию.
3. **Fail-closed при исчерпании цепочки**: если все провайдеры цепочки
   отклонили результат или недоступны, предпросмотр завершается failed-closed
   без применимого патча. Методолог получает категорию ошибки из раздела 11;
   путь дальше — только новый явный запрос (новый idempotency key).
4. **Неблокирующие предупреждения vs blocking FAIL**: предупреждения
   (например, `correct_answer_length_signal`, `rote_recall_only`) остаются
   внутри применимого предпросмотра со статусом `applicable_with_warnings` и
   не триггерят отклонение или fallback. Blocking FAIL — любое из оснований
   пункта 1 — делает результат неприменимым: отклонение, возможный fallback
   по пункту 2, либо fail-closed по пункту 3.

Validator-blocked результат никогда не становится применимым сам по себе.
Контролируемый переход к следующему провайдеру допустим только потому, что его
новый результат заново проходит те же блокирующие проверки; при исчерпании
цепочки действует fail-closed, а не ослабление требований.

## 9. Устаревшие версии (stale behavior)

- Предпросмотр всегда привязан к base version из snapshot.
- К моменту apply содержимое могло измениться: если текущая версия не
  совпадает с base version предпросмотра, apply отклоняется, предпросмотр
  помечается `stale`.
- Stale-предпросмотр не перегенерируется автоматически молча: методолог
  получает сообщение и явное действие «запросить заново» (новый idempotency
  key, новая цепочка `requested → preview_ready`).
- Результат валидатора, полученный против старой версии, не переносится на
  новую: регенерация включает полный повтор валидации.

## 10. Идемпотентные повторы

Правила повторов наследуют контракт Step 2 (сценарии 8–9 там) и уточняются
для провайдер-вызова:

- Повторная отправка той же команды при транспортном сбое несёт тот же
  стабильный idempotency key и возвращает исходные request и предпросмотр;
  провайдер не вызывается второй раз.
- Идемпотентность apply отдельна: apply по паре `(request identifier,
  base version)` не создаёт вторую ревизию.
- Коллизия idempotency (тот же key, другая нагрузка) отклоняется fail-closed.
- Осознанный новый запрос («Другой вариант») несёт новый key и создаёт новую
  цепочку; параллельные предпросмотры не мутируют контент, применён может
  быть один, второй после apply становится stale.
- Незавершённый вызов провайдера (обрыв, таймаут без ответа) не считается
  результатом: повтор с тем же key обязан либо вернуть завершённый исходный
  предпросмотр, либо выполнить вызов ровно один раз — двойное списание вызова
  на одном key исключается.

## 11. Безопасные категории ошибок

Ошибки возвращаются методологу закрытым каталогом сообщений (по одной
канонической формулировке на категорию и локаль). Категории:

| Категория | Смысл | Раскрытие методологу |
|---|---|---|
| `provider_timeout` | провайдер не ответил вовремя | «Предпросмотр не успел сформироваться. Повторите запрос.» |
| `provider_unavailable` | маршрут недоступен, fallback не дал результата | «Сервис генерации временно недоступен. Попробуйте позже.» |
| `provider_output_unparseable` | ответ не разобран | «Сервис вернул некорректный результат. Повторите запрос.» |
| `contract_violation` | патч нарушает схему/ограничения | «Предложение нарушает ограничения операции. Измените запрос.» |
| `validation_blocked` | блокирующие findings валидатора | список findings по каталогу Step 3 |
| `stale_base_version` | содержимое изменилось | «Содержимое изменилось. Запросите предложение заново.» |
| `rejected_out_of_scope` | запрос вне полномочий | объяснение границы и альтернатива |
| `internal_error` | остальное | нейтральное сообщение без технических деталей |

Запрещено раскрывать в ошибках: raw-инструкцию, тексты фрагментов, тексты
патча, tenant identifiers, внутренние идентификаторы провайдера, стектрейсы
(правило разделов 2 и 5: tenant-scoped сырые поля не попадают в сообщения об
ошибках). Техническая детализация остаётся в серверной телеметрии без
чувствительных полей.

## 12. Синтетические примеры по категориям намерений

Все примеры используют базовое синтетическое окружение из спецификации
Step 2: курс «Охрана труда для офиса», урок 1.2 «Электробезопасность»,
вопрос 3, источник «Правила работы с электрооборудованием (образец)»,
раздел 4 (`fragment E01`), локаль `ru`.

### 12.1 Wording — `rewrite_wording`

- Запрос: «Переформулируй вопрос проще».
- Вход: `field_scope: [question.text]`, `preserve_correct_answer`.
- Ожидаемый патч: `update_field { entity: question, field: text }` — только
  текст; варианты и correct index не тронуты.
- Ожидание валидатора: `malformed_question` отсутствует; статус `applicable`.
- Провенанс: провайдер, модель и промпт версии записаны с результатом.

### 12.2 Context — `add_context`

- Запрос: «Добавь рабочую ситуацию: сотрудник подключает удлинитель на
  складе».
- Вход: `field_scope: [question.text]`, `grounded_in_source`.
- Ожидаемый патч: prepend вводной фразы; `source_evidence` ссылается на
  `E01`, если фраза опирается на него.
- Ожидание валидатора: если добавленное утверждение не выводится из `E01` и
  текущего текста — предупреждение/блокировка по семантике
  `unsupported_correct_answer`; при подтверждённой фразе — `applicable`.

### 12.3 Distractors — `regenerate_distractors`

- Запрос: «Сделай неверные варианты менее очевидными, правильный не трогай».
- Вход: `field_scope: [answer_options]`, `scope: distractors_only`,
  `preserve_correct_answer`, `refutable_from_source`.
- Ожидаемый патч: `replace_collection` с новыми Б–Г и моделью заблуждения на
  каждый; correct index отсутствует в патче.
- Ожидание валидатора: дистракторы правдоподобны и опровергаемы из `E01`;
  `implausible_distractors` отсутствует; нарушение `preserve_correct_answer`
  где-либо — `not_applicable`.

### 12.4 Answer balance — `balance_answer_length`

- Запрос: «Вариант А заметно длиннее — выровняй подробность».
- Вход: `field_scope: [answer_options]`, `preserve_correct_answer`.
- Ожидаемый патч: `update_field` по каждому дистрактору; сокращение
  правильного ответа без явного разрешения не выполняется.
- Ожидание валидатора: предупреждение `correct_answer_length_signal`
  снимается; если два варианта становятся равно-подтверждаемыми —
  `multiple_plausible_correct_answers`, статус `not_applicable`.

### 12.5 Difficulty — `change_difficulty`

- Запрос: «Сделай вопрос сложнее».
- Вход: `field_scope: [question.text, answer_options, explanation]`,
  `preserve_correct_answer` (факт сохраняется, оболочка усложняется).
- Ожидаемый патч: переформулировка вопроса и/или дистракторов с более тонкой
  моделью заблуждения; атомарный факт и правильный вариант не меняются.
- Ожидание валидатора: усложнение не создаёт второй подтверждаемый вариант
  (`multiple_plausible_correct_answers` — блокировка); сложность записана
  структурным полем патча.

### 12.6 Scenario — `make_scenario_based`

- Запрос: «Преврати вопрос в практическую ситуацию».
- Вход: `field_scope: [question.text]`, `grounded_in_source`.
- Ожидаемый патч: `update_field { entity: question, field: text,
  operation: replace }` — ситуация с действием сотрудника; варианты
  по умолчанию не меняются.
- Ожидание валидатора: снимается предупреждение `rote_recall_only`;
  ситуация подтверждается `E01` либо предупреждение о неподтверждённой
  детали; статус `applicable` при подтверждённой ситуации.

### 12.7 Explanation — `add_or_rewrite_explanation`

- Запрос: «Перепиши пояснение понятнее».
- Вход: `field_scope: [explanation]`, `preserve_correct_answer`.
- Ожидаемый патч: `update_field { entity: explanation, field: text }`.
- Ожидание валидатора: пояснение не содержит дословного текста вариантов
  (проверка `explanation_leaked_into_answer`); нарушение — блокировка,
  статус `not_applicable`.

### 12.8 Source verification — `fix_source_grounding`

- Запрос: «Проверь, что правильный ответ подтверждается источником».
- Вход: `field_scope: [question.correct_answer, source_evidence]`,
  `preserve_correct_answer` (проверка не меняет ответ).
- Ожидаемый патч: при подтверждении — нет операций над контентом, только
  зафиксированная привязка `source_evidence`; при неподтверждении —
  предложение методологу с указанием, какой факт в `E01` есть, без
  самовольной подмены ответа.
- Ожидание валидатора: неподтверждённый правильный ответ при явных
  фрагментах — блокирующий `unsupported_correct_answer`, статус
  `not_applicable` до явного решения методолога; подтверждённый — статус
  `applicable` без операций.

### 12.9 Сводная таблица примеров

| # | Категория | Scope патча | Ключевая проверка | Итог применимости |
|---|---|---|---|---|
| 1 | `rewrite_wording` | `question.text` | полнота формулировки | applicable |
| 2 | `add_context` | `question.text` | grounded in source | applicable / warnings |
| 3 | `regenerate_distractors` | distractors only | `preserve_correct_answer`, опровержимость | applicable |
| 4 | `balance_answer_length` | distractors | пороги длины | applicable / not_applicable |
| 5 | `change_difficulty` | question + options | единственность правильного | applicable / not_applicable |

| 8 | `fix_source_grounding` | evidence only | `unsupported_correct_answer` | applicable / not_applicable |

## 13. Общие инварианты контракта

1. Провайдер предлагает; сервер решает: применимость присваивается только
   после детерминированной валидации, никогда на стороне модели.
2. Payload провайдера содержит bounded raw-инструкцию методолога и минимальное
   выбранное содержимое вопроса/вариантов/свидетельств, необходимое для
   редактирования; дайджест не заменяет инструкцию. Эти tenant-scoped сырые
   поля разрешены только в request провайдера по утверждённому контракту
   обработки; payload не содержит tenant identifiers и данные за пределами
   выбранного вопроса.
3. Tenant-scoped сырые поля (raw-инструкция, содержимое вопроса, фрагменты)
   запрещены в обычных логах, метриках и их label-ах, cross-tenant и
   маркетинговой аналитике, сообщениях об ошибках и провенанс-полях.
4. `preserve_correct_answer` и все ограничения применяются сервером и не
   могут быть ослаблены содержимым ответа модели.
5. Malformed, scope-escaping, нарушающий `preserve_correct_answer`,
   evidence-invalid или validator-blocked результат провайдера отклоняется
   целиком и может триггерить контролируемый fallback к следующему провайдеру
   утверждённой цепочки с ровно теми же гейтами parser/scope/evidence/
   validator. Fallback никогда не ослабляет и не пропускает валидацию.
6. При исчерпании цепочки (все провайдеры отклонили или недоступны)
   предпросмотр завершается fail-closed без применимого патча.
7. Неблокирующие предупреждения могут оставаться в применимом предпросмотре
   (`applicable_with_warnings`); blocking FAIL — всегда отклонение.
8. Повторы идемпотентны; двойной вызов провайдера на одном key исключён;
   коллизия — fail-closed.
9. Stale-предпросмотр отклоняется и регенерируется только явно.
10. Телеметрия содержит только нормализованные поля; тексты и персональные
    данные не попадают в логи, метрики и аналитику.
11. Все содержимое этого документа синтетическое; реальные данные клиентов
    не включены и не должны добавляться.
